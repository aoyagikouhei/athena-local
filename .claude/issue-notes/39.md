| 文 | hive | iceberg | 本物の `SubstatementType` |

### 決め手: **カタログ単位で形式を判定できる**

```sql
SELECT connector_name FROM system.metadata.catalogs WHERE catalog_name = '<カタログ名>'
```

が `hive` / `iceberg` をそのまま返す。Trino の Hive コネクタと Iceberg コネクタは**別カタログとして
設定する以外に共存できず、1 つのカタログに両形式のテーブルが混在することは構造上あり得ない**。
したがって **SQL からテーブル名を取り出す必要が無い**。`execution.rs:335-339` が既に解決している
`catalog` をそのまま使える。**設計の難所のうち「テーブル名の抽出」が丸ごと消えた。**

対象テーブルの存在に関係なく常に応答するので、`DROP TABLE IF EXISTS` で対象が無いときの
扱いも問題にならない（未確認事項だった 3 件目が解消）。

### 形式を知る手段の比較（実測）

| 手段 | 可否 | 形式が読めるか |
|---|---|---|
| **`system.metadata.catalogs` の `connector_name`** | **使える（本命）** | **`hive` / `iceberg` がそのまま。カタログ単位** |
| `SHOW CATALOGS` | 使える | 読めない（名前の列挙だけ） |
| `SHOW CREATE TABLE` | 使える | 部分的。本文の `WITH (...)` を解析する必要があり脆い。SQL 本文を読まない方針にも反する |
| `information_schema.tables` | 使える | 読めない（`table_type` は両方 `BASE TABLE`） |
| `"<table>$properties"` | 使える | 読める（行の形が違う）が、テーブル名と存在確認が要る |
| `system.metadata.table_properties` | 使える | 目的に合わない（コネクタが受け付けるプロパティ定義の一覧で、テーブル単位ではない） |

### `updateType`（41B / 38B の中身に要る）

**Trino は `DROP TABLE` に `updateType: "DROP TABLE"` を返す。** 本物の Athena が `.metadata` の
field 2 に書く文字列と同じ。`ALTER TABLE ... ADD COLUMN` には `updateType: "ADD COLUMN"`
（Athena の `ADD COLUMNS` とは綴りが違うが、38B には field 2 自体が無いので影響しない）。

**Hive と Iceberg で Trino の応答は完全に同一**（`id` 以外バイト単位で同じ）。つまり
Trino の応答そのものからは形式を読み取れず、本物の Athena が見せる差は Athena エンジン側の
実装差。カタログを別クエリで聞く以外に手段は無い。

### この実測で解消した未検証の前提

1. ~~Trino が `DROP TABLE` に `updateType` を返すか~~ → **返す（`DROP TABLE`）**
2. ~~Trino でテーブル形式を知る手段~~ → **`system.metadata.catalogs` の `connector_name`。カタログ単位**
3. ~~`DROP TABLE IF EXISTS` で対象が無いとき~~ → **カタログ単位なので問題にならない**

### 残る前提（実装の設計で扱う）

- **Athena と Trino の非対称**: Athena は同じ `AwsDataCatalog` に Hive と Iceberg が混在するが、
  Trino は別カタログ。athena-local の判定は**利用者の Trino のカタログ構成に従う**ことになり、
  本物と一致するのは「Athena 側のテーブル形式と Trino 側のカタログの形式が揃っている」場合だけ。
  これは再現精度の上限で、README の Caveats に書く
- **カタログが未指定のとき**（`TRINO_CATALOG` も `QueryExecutionContext.Catalog` も無い）は
  問い合わせる対象が無いので判定できない。従来どおりの振る舞い（置かない）に倒す必要がある

### 修飾名からカタログを読む（新しい実装範囲）

`alias_qualified_names`（`catalog.rs:21-55`）は**全文を走査して別名マップのキーと一致する引用符付き識別子を置換する**関数で、
今回要る「先頭の文の修飾名の第 1 パートを取り出す」処理とは別物。再利用できるのは字句の読み飛ばし
（`skip_quoted`:58・`comment_end`:75・`unquote`:132。いずれも private なので `pub(crate)` に上げる）。

扱う形（テストで固定する）:

| SQL | カタログ |
|---|---|
| `DROP TABLE cat.ns.t` | `cat`（3 パート） |
| `DROP TABLE "s3tablescatalog/my-bucket".ns.t` | 引用符付きの第 1 パート |
| `DROP TABLE ns.t` | 指定なし → 既定カタログ（2 パート） |
| `DROP TABLE t` | 指定なし → 既定カタログ |
| `DROP TABLE IF EXISTS cat.ns.t` | `IF EXISTS` を読み飛ばして `cat` |
| `DROP TABLE /* c */ cat.ns.t` | コメントを読み飛ばして `cat` |

引用符の無い名前の大文字小文字は Trino の規則（小文字化）に合わせる。判定に使うのは
**別名解決後**の名前（`config.trino_catalog()` を通した値。計画レビュー G）。

| 4 | 対象が存在しない `DROP TABLE IF EXISTS` で本物と食い違う | **Phase 2 でテーブルの存在も確かめる** | `IF EXISTS` 付きの冪等な DDL は実務でよく使われ、対象外にすると存在するときまで食い違う | ○ |
| 5 | 未実装の `SubstatementType` 3 値 | **今回実装する** | 3 つとも実測値で推測ではない。ALTER の判定を位置固定に締めるときに match の腕を足すだけで済む | ○ |

### Phase 2 の設計（統括役が決めた）

**存在確認は `system.jdbc.tables` を使う。**`table_cat` / `table_schem` / `table_name` を**全部リテラルで**書けるので、
カタログ名を識別子として SQL に埋め込まずに済む（識別子のクォートを手書きしない）。
`<catalog>.information_schema.tables` だとカタログ名が識別子になるので採らない。

形式と存在を **1 つのクエリ**にまとめ、往復を 1 回に保つ:

```sql
SELECT
  (SELECT connector_name FROM system.metadata.catalogs WHERE catalog_name = '<cat>'),
  (SELECT count(*) FROM system.jdbc.tables
    WHERE table_cat = '<cat>' AND table_schem = '<ns>' AND table_name = '<t>')
```

修飾名の解析（`parse_drop_target`）:

| SQL | catalog | schema | table |
|---|---|---|---|
| `DROP TABLE t` | 既定（`execution.catalog`） | 既定（`execution.database`） | `t` |
| `DROP TABLE ns.t` | 既定 | `ns` | `t` |
| `DROP TABLE cat.ns.t` | `cat` | `ns` | `t` |
| `DROP TABLE "s3tablescatalog/x".ns.t` | 引用符を外した第 1 パート | `ns` | `t` |
| `DROP TABLE IF EXISTS cat.ns.t` | `IF EXISTS` を読み飛ばして `cat` | `ns` | `t` |

- **修飾名から取ったカタログにも `config.trino_catalog()` で別名を当てる**（`execution.catalog` と同じ扱い。計画レビュー G）
- catalog か schema が決まらなければ判定しない（今までどおりに倒す）
- 引用符の無い名前は Trino の規則に合わせて小文字にする
- 再利用するのは `catalog.rs` の `skip_quoted`(58)・`comment_end`(75)・`unquote`(132)。private なので `pub(crate)` に上げる

### Phase 3 の範囲（実測で確定）

1. **`classification.rs` の ALTER 判定を位置固定に締める**（`word(3) == "ADD" && word(4).starts_with("COLUMN")`）。
   `SET TBLPROPERTIES ('comment'='...add column...')` の誤判定が消える
2. **`SubstatementType` に実測値 3 つを足す**: `ALTER_TABLE_PROPERTIES`（`SET TBLPROPERTIES`）・
   `ALTER_TABLE_DROP_COLUMN`（`DROP COLUMN`）・`ALTER_TABLE_SET_LOCATION`（`SET LOCATION`）
3. **`ALTER TABLE ... ADD COLUMNS` × Hive** に 38B の `.metadata` と `application/octet-stream` を置く。
   本体は 0 バイトのまま（`EngineDdl` のバリアントで body を分けるのはそのため）
4. 38B は field 1 の `QueryExecutionId` のみ。`write_metadata` の直前で `(id, None, None)` に上書きする
   （Trino の `updateType` は `"ADD COLUMN"` で Athena の綴りと違うため、そのまま使うと誤った field 2 が付く）

`ALTER TABLE IF EXISTS` と `RENAME COLUMN` は Athena に構文が無いので、位置固定の判定なら自然に対象外になる
（`word(3)` が `EXISTS` / `RENAME` になる）。実測できない形を推測で埋めないという方針と一致する。

## Step 8 の結果（4 ゲートで裁いた。棄却 0 件）

### 1. ALTER の判定がトリビアを跨げない（**3 本が独立に指摘**。high）

位置固定の判定（`word(3)` / `word(4)`）が `words()` ベースなので、テーブル名の後ろに何か挟まると位置がずれる。
**旧実装（全文走査）では通っていた入力が `None` に落ちる回帰。**

| 入力 | 見つけた層 |
|---|---|
| `ALTER TABLE "my table" ADD COLUMNS (c string)` | 独立レビュー |
| `ALTER TABLE cat . ns . t ADD COLUMNS (m int)` | 最終パス（削除された振る舞い） |
| `ALTER TABLE t -- comment\nADD COLUMN c int` | 同上 |
| `ALTER TABLE t /* c */ ADD COLUMNS (m int)` | 最終パス（逐行） |

影響は 2 段階。`SubstatementType` が欠落するだけでなく、`table_format::target_statement` がこの値を使うので
**本 issue の本題（38 バイトの `.metadata`）も発動しなくなる**。

**構造的な指摘**: `table_format.rs` の `table_name_start` は各トークン境界で `skip_leading_trivia` を挟んで
コメント耐性を持たせてあるのに、その手前の `classification.rs` の判定がコメントに弱いせいで、その耐性が活きていない。
「判定を二重に持たない」設計が、退行を `classification` から `table_format` へそのまま伝播させていた。

**対応**: 全文走査には戻さない（`SET TBLPROPERTIES` の誤判定が復活するため）。`catalog.rs` に修飾名を読み飛ばす
関数を足し、キーワードごとに `skip_leading_trivia` を挟んで読み進める形にする。

### 2. `SET TBLPROPERTIES(` の空白なしが判定できない（最終パス。medium）

`("SET", "TBLPROPERTIES")` が完全一致なので、`SET TBLPROPERTIES('comment' = 'x')` は `word(4)` が
`TBLPROPERTIES('COMMENT'` になって落ちる。回帰ではない（旧実装は判定していなかった）が、Phase 3a で足した分岐の漏れ。
**対応**: 1 の字句走査に寄せる形で一緒に直す。

### 3. S3 書き込みが無効でも形式の問い合わせが走る（最終パス。medium）

`probe_format` が `config.results` を見ないので、S3 を設定していない構成でも `DROP TABLE` / `ALTER` のたびに
Trino へのフル往復が発生し、結果は `write_result` の入口（`app.results` が `None`）で捨てられる。
結果 CSV の書き込みは README で「オプション」なので、現実に踏む。
**対応**: `run` で S3 が無効なら `target_statement` / `probe_format` を呼ばない。

### 4. テストの assert が不必要に緩い（最終パス。low-medium）

`引用符付きのカタログ名にも別名を当てて問い合わせる` だけ `starts_with` / `ends_with` になっていた。
レビューが `catalog.rs::replacement` のパディング計算を実際に走らせ、**期待値は決定的**（閉じ引用符の後ろにスペース 10 個）
と確認。「本来通らない期待値の回避」ではなく手計算の手間を避けた緩和だった。
**対応**: 完全一致に戻す。

### 問題なしと判断された点（3 本に共通）

`ResultWriter::put` / `write_metadata` / `run` のシグネチャ変更と呼び出し元の整合、`catalog.rs` の可視性拡張、
41B / 38B の field の出し分け、`Option` の運び方（`.ok()?` で今までどおりに倒す設計）、取り消しと probe の順序・伝播。

### design-checklist に足した教訓（2 行）

- 全文走査を位置固定に変えるとき、判定位置の手前に挟まるトリビアを列挙したか
- 新しい外部への問い合わせが、結果を使わない設定でも走らないか

## Trino のバージョン差（人間検証リスト 1 番目。2026-09-21）

`connector_name` が小文字の `hive` / `iceberg` を返すことに実装が依存しているので、バージョン差を確かめた。
足場は `39-trino-probe` の compose を `${TRINO_TAG:-482}` で差し替えられるように直したもの。

| 確認項目 | Trino 482 | Trino 483 |
|---|---|---|
| `system.metadata.catalogs` の `connector_name` | `hive` / `iceberg`（小文字） | **同じ** |
| probe（形式 + 存在の 1 クエリ）: 存在する Hive | `[["hive", 1]]` | **同じ** |
| probe: 存在しない Iceberg | `[["iceberg", 0]]` | **同じ** |
| `DROP TABLE` の `updateType` | `DROP TABLE` | **同じ** |
| `ALTER ... ADD COLUMN` の `updateType` | `ADD COLUMN` | **同じ** |

**隣接する 2 バージョンでは差が無い。**それより古いバージョンは確かめられていない
（`fs.local.enabled` が 482 で正式名になった等の設定差があり、`./catalog-legacy` を用意する途中で止めた）。

実装は `hive` でも `iceberg` でもない値を `None` に倒すので、**将来のバージョンで値が変わっても壊れるのではなく
「判定しない（＝今までどおり）」に落ちる**。安全側の失敗なので、古いバージョンの未確認は残して出荷してよいと判断した。

### 委譲先が止まった件（記録）

このバージョン差の委譲先は、3 つ目（古いバージョン）のコンテナを立てようとして
`Container is still starting (health check pending)` のまま **32 分ループして返らなかった**。
イメージが取得できておらず（`docker images` に無い）コンテナも起動していないのに待ち続けていた。
`TaskStop` で止め、**生データは 482 / 483 とも揃っていたので統括役が自分で読んだ**。
後始末（`docker compose down -v`）も統括役が実行した（エージェントを止めたので trap が効かない）。

→ implement-issue の「委譲先が期限内に返らなければ自分で引き取る」「Step 9 は目安 10 分」の線を
32 分まで引っ張ってしまった。**docker の状態（イメージ・コンテナ・pull の有無）を見れば実作業が
終わっていることは分かったので、もっと早く止められた。**
