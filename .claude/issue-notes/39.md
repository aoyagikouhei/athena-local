## 実測の結果（2026-09-20〜21。3 ラウンドを統合）

本物の Athena（engine version 3）で 3 ラウンド。**形式だけを変えた対を同じラウンドに入れて測った**（#26 の教訓）。
`table_format` は `SHOW CREATE TABLE` による裏取り。

### DROP TABLE（ラウンド 1・2 で確定、3 でも再現）

| 消したテーブル | 本体 | 本体 CT | `.metadata` |
|---|---|---|---|
| hive（CTAS 作成 / 素の CREATE 作成のどちらも） | 0B | binary | 無し |
| **iceberg（同上）** | **1B = 改行 1 つ** | **application** | **41B** |
| **対象が存在しない `IF EXISTS`** | **0B** | **binary** | **無し** |

作り方（CTAS か素の CREATE か）では変わらない。**対象が存在しないときは形式を持ちようがないので Hive 側と同じ**
（ラウンド 3 の `g`）。これは athena-local がカタログ単位で判定すると食い違う唯一のケース。

### ALTER TABLE（ラウンド 3 で確定）

| 文 | hive | iceberg | 本物の `SubstatementType` |
|---|---|---|---|
| `SET TBLPROPERTIES ('comment' = '...add column...')` | 0B / 無し / binary | FAILED（`comment` 不可） | **`ALTER_TABLE_PROPERTIES`** |
| **`ADD COLUMNS (m int)`** | 0B / **38B** / **application** | 0B / 無し / binary | `ALTER_TABLE_ADD_COLUMN` |
| `DROP COLUMN` | FAILED（Hive の制約） | 0B / 無し / binary | **`ALTER_TABLE_DROP_COLUMN`** |
| `SET LOCATION` | 0B / 無し / binary | （Hive のみ測定） | **`ALTER_TABLE_SET_LOCATION`** |
| `IF EXISTS ... ADD COLUMNS` | START_FAILED | START_FAILED | - |
| `RENAME COLUMN` | START_FAILED | START_FAILED | - |

**`.metadata` を置く ALTER は `ADD COLUMNS` × Hive だけ。**
`ALTER TABLE IF EXISTS` と `RENAME COLUMN` は**Athena に構文が無い**（`mismatched input`。MALFORMED_QUERY）。
どちらも両形式で同じ結果なので、構文の問題でテーブルの形式とは無関係。

### 分かったこと

1. **差は「Iceberg かどうか」では決まらない。** `DROP TABLE` は Iceberg 側が置き、`ADD COLUMNS` は Hive 側が置く。
   向きが逆で、中身の形も違う（41B はエンジン ID + `DROP TABLE`、38B は `QueryExecutionId` のみ）
2. **本体の Content-Type と `.metadata` の有無が完全に相関する。** 成功した文で本体が
   `application/octet-stream` なのは `b1`（ADD COLUMNS × Hive）と `f`/`h2`（DROP × Iceberg）だけで、
   その 3 つだけが `.metadata` を持つ。`5.md:53` の「`UpdateCount` を返さない文が素の protobuf を持つ」と同じ切り口
3. **本物は ALTER の種類を正しく区別している。** `SET TBLPROPERTIES` は `ALTER_TABLE_PROPERTIES`、
   `ADD COLUMNS` は `ALTER_TABLE_ADD_COLUMN`。athena-local が前者に `ALTER_TABLE_ADD_COLUMN` を返すのは
   **誤りと実測で確定**（計画レビュー A の裏づけ）
4. **athena-local が返していない `SubstatementType` が 3 つある**: `ALTER_TABLE_PROPERTIES`・
   `ALTER_TABLE_DROP_COLUMN`・`ALTER_TABLE_SET_LOCATION`（すべて実測値）
5. **1 バイトの正体は改行 1 つ**（`0a`）。`1.md` の 2026-09-16 の記録を形式の裏取り付きで再現。
   過去 3 ラウンドと今回はすべて整合し、食い違いは無い

## Trino 側の実測（Step 3b の 2 本目。2026-09-20）

ローカルに `trinodb/trino:482` を立てて測った（本物の AWS は使っていない）。
足場は `.claude/issue-notes/39-trino-probe/`（compose・カタログ設定・`probe.sh`）。

**決め手: カタログ単位で形式を判定できる。**

```sql
SELECT connector_name FROM system.metadata.catalogs WHERE catalog_name = '<カタログ名>'
```

が `hive` / `iceberg` を返す。Trino の Hive コネクタと Iceberg コネクタは**別カタログとしてしか共存できず**、
1 つのカタログに両形式が混在することは構造上あり得ない。したがって **SQL からテーブル名を取り出さなくても
判定できる**（#26 が撤回した「SQL から形式を読む」やり方に戻らずに済む）。

ほかの手段（`SHOW CATALOGS`・`SHOW CREATE TABLE`・`information_schema.tables`・`$properties`・
`system.metadata.table_properties`）は、読めないか、テーブル名と存在確認が要るか、本文の解析が要るかで、
いずれも `connector_name` に劣る。

**`updateType`**: Trino は `DROP TABLE` に `updateType: "DROP TABLE"` を返す（本物の Athena が 41B の
field 2 に書く文字列と同じ）。`ALTER TABLE ... ADD COLUMN` には `"ADD COLUMN"`（Athena の `ADD COLUMNS` と
綴りが違うが、38B には field 2 自体が無いので影響しない）。**Hive と Iceberg で Trino の応答は完全に同一**で、
Trino の応答そのものからは形式を読み取れない。

**残る前提（Caveats に書いた）**: Athena は同じ `AwsDataCatalog` に両形式を混在させるが Trino は別カタログ。
athena-local の判定は利用者の Trino のカタログ構成に従うので、本物と一致するのは両者の形式が揃っている場合だけ。

### 修飾名からカタログを読む（新しい実装範囲）

`alias_qualified_names`（`catalog.rs:21-55`）は**全文を走査して別名マップのキーと一致する引用符付き識別子を置換する**関数で、
今回要る「先頭の文の修飾名の第 1 パートを取り出す」処理とは別物。再利用できるのは字句の読み飛ばし
（`skip_quoted`:58・`comment_end`:75・`unquote`:132。いずれも private なので `pub(crate)` に上げる）。

扱う形（テストで固定する）:

| SQL | カタログ |
|---|---|
| `DROP TABLE cat.ns.t` | `cat`（3 パート） |
| `DROP TABLE "s3tablescatalog/my-bucket".ns.t` | 引用符付きの第 1 パート |
| `DROP TABLE ns.t` | 指定なし → 既定カタログ（2 パート） |
| `DROP TABLE t` | 指定なし → 既定カタログ |
| `DROP TABLE IF EXISTS cat.ns.t` | `IF EXISTS` を読み飛ばして `cat` |
| `DROP TABLE /* c */ cat.ns.t` | コメントを読み飛ばして `cat` |

引用符の無い名前の大文字小文字は Trino の規則（小文字化）に合わせる。判定に使うのは
**別名解決後**の名前（`config.trino_catalog()` を通した値。計画レビュー G）。

## Step 8 の結果（4 ゲートで裁いた。棄却 0 件）

### 1. ALTER の判定がトリビアを跨げない（**3 本が独立に指摘**。high）

位置固定の判定（`word(3)` / `word(4)`）が `words()` ベースなので、テーブル名の後ろに何か挟まると位置がずれる。
**旧実装（全文走査）では通っていた入力が `None` に落ちる回帰。**

| 入力 | 見つけた層 |
|---|---|
| `ALTER TABLE "my table" ADD COLUMNS (c string)` | 独立レビュー |
| `ALTER TABLE cat . ns . t ADD COLUMNS (m int)` | 最終パス（削除された振る舞い） |
| `ALTER TABLE t -- comment\nADD COLUMN c int` | 同上 |
| `ALTER TABLE t /* c */ ADD COLUMNS (m int)` | 最終パス（逐行） |

影響は 2 段階。`SubstatementType` が欠落するだけでなく、`table_format::target_statement` がこの値を使うので
**本 issue の本題（38 バイトの `.metadata`）も発動しなくなる**。

**構造的な指摘**: `table_format.rs` の `table_name_start` は各トークン境界で `skip_leading_trivia` を挟んで
コメント耐性を持たせてあるのに、その手前の `classification.rs` の判定がコメントに弱いせいで、その耐性が活きていない。
「判定を二重に持たない」設計が、退行を `classification` から `table_format` へそのまま伝播させていた。

**対応**: 全文走査には戻さない（`SET TBLPROPERTIES` の誤判定が復活するため）。`catalog.rs` に修飾名を読み飛ばす
関数を足し、キーワードごとに `skip_leading_trivia` を挟んで読み進める形にする。

### 2. `SET TBLPROPERTIES(` の空白なしが判定できない（最終パス。medium）

`("SET", "TBLPROPERTIES")` が完全一致なので、`SET TBLPROPERTIES('comment' = 'x')` は `word(4)` が
`TBLPROPERTIES('COMMENT'` になって落ちる。回帰ではない（旧実装は判定していなかった）が、Phase 3a で足した分岐の漏れ。
**対応**: 1 の字句走査に寄せる形で一緒に直す。

### 3. S3 書き込みが無効でも形式の問い合わせが走る（最終パス。medium）

`probe_format` が `config.results` を見ないので、S3 を設定していない構成でも `DROP TABLE` / `ALTER` のたびに
Trino へのフル往復が発生し、結果は `write_result` の入口（`app.results` が `None`）で捨てられる。
結果 CSV の書き込みは README で「オプション」なので、現実に踏む。
**対応**: `run` で S3 が無効なら `target_statement` / `probe_format` を呼ばない。

### 4. テストの assert が不必要に緩い（最終パス。low-medium）

`引用符付きのカタログ名にも別名を当てて問い合わせる` だけ `starts_with` / `ends_with` になっていた。
レビューが `catalog.rs::replacement` のパディング計算を実際に走らせ、**期待値は決定的**（閉じ引用符の後ろにスペース 10 個）
と確認。「本来通らない期待値の回避」ではなく手計算の手間を避けた緩和だった。
**対応**: 完全一致に戻す。

### 問題なしと判断された点（3 本に共通）

41B / 38B の field の出し分け、`Option` の運び方（`.ok()?` で今までどおりに倒す設計）、取り消しと probe の順序・伝播。

|---|---|---|
| `ALTER TABLE <hive> /* c */ ADD COLUMN m2 int` | 判定が効かず 0B・`.metadata` 無し | **0B・application・38B** |
| `DROP TABLE "<iceberg>"`（引用符付き） | 同上 | **1B（`0a`）・application・41B** |

レビューが指摘した回帰の修正が、偽サーバだけでなく本物の Trino と MinIO でも効いていることの裏づけ。

### 未確認のまま残っているもの（JDBC）

**今回 `.metadata` を「置く」ようになったが、それを JDBC クライアントが読めるかは誰も確かめていない。**
41B も 38B も**列を 1 つも持たない protobuf** で、`.metadata` 本来の用途（列情報を渡す）から外れた形。

`5.md` の実機検証は「`.metadata` を**置かない**ときに JDBC 3.8.1 が 404 を INFO で流して続行する」ことを
確認したが、**「列 0 個の `.metadata` を置いたとき」は新しい経路**。ここで例外が出ると
`ResultFetcher=auto` の利用者に実害が出る。athena-local 相手の確認なので人間でなくてもできる。
