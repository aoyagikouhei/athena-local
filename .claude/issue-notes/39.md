## 実測の結果（2026-09-20）

`39-measure-drop-table-format.sh` を本物の Athena（engine version 3）で 1 ラウンド。
**形式だけを変えた対を同じラウンドに入れて測った**（#26 の教訓）。`table_format` は
`SHOW CREATE TABLE` による裏取り。

| h | `DROP TABLE`（素の CREATE で作成） | **iceberg** | **1B `newline-only`** | **application/octet-stream** | **41B** |

**分かったこと**

1. **差は `DROP TABLE` に固有**。Iceberg のテーブルでも `CREATE TABLE`（b）と
   `ALTER TABLE`（d2）は 0B・`.metadata` 無しで、Hive と同じだった。「Iceberg への DDL は
   全部違う」ではない。
2. **1 バイトの正体は改行 1 つ**（`f.body.od.txt` が `0a` 1 バイト）。`1.md` が 2026-09-16 に
   記録した「1 バイトで中身は改行 1 つだけ」を、形式の裏取り付きで独立に再現した。
   そのときのテーブルも Iceberg だった（`1-measure-txt.sh:159` の
   `TBLPROPERTIES ('table_type'='ICEBERG')`）ので、過去の実測との食い違いは無い。
3. **`.metadata` 41B の中身**を生データで確認した。`0a 1b` + 27 バイトのエンジンのクエリ ID
   （`20260920_110028_00079_sviss` の形）、`12 0a` + `DROP TABLE`（10 バイト）で 41B ちょうど。
   更新件数（field 3）も列（field 4）も無い。issue のコメントの読みどおりで、既存の
   `metadata.rs` がそのまま組み立てられる形。
4. **Content-Type も割れている**。Iceberg の DROP だけ `application/octet-stream` で、
   ほかの `<id>.txt`（Hive の DROP を含む）は `binary/octet-stream`。README は多数派の
   binary を送ると書いてあり、athena-local は常に binary を送る。

## 未実測のまま残るもの（2 ラウンド目で埋める）

1 ラウンド目で測れなかった 5 項目。スクリプトは修正済みで、同じコマンドをもう一度
走らせれば測れる。

- Hive の素の `CREATE TABLE`（a）。1 ラウンド目は `CREATE TABLE t (n int)` を投げて
  `No location was specified for table`（MALFORMED_QUERY）で開始自体が失敗した。
  → `CREATE EXTERNAL TABLE ... LOCATION '<OUTPUT>tables-probe-39-hive-plain/'` に直した
- Hive の `ALTER TABLE` ×2（c1 / d1）と、素の CREATE で作った Hive テーブルの `DROP`（g）。
  a に依存する gate で SKIP された
- Iceberg の `ALTER TABLE ... SET TBLPROPERTIES`（c2）。`comment` は Iceberg で
  `Unsupported table property key` になる。→ `vacuum_max_snapshot_age_seconds` に直した

## 引き継ぎ（implement-issue へ）

反映方針はユーザーの選択で「**Trino に問い合わせて本物に合わせる**」（README の Caveats に
差として書くだけ、ではない）。CLAUDE.md の「文の先頭のキーワードだけを見る」「SQL の本文は
書き換えない」という約束に対して、DROP の前にテーブルの形式を別のクエリで確かめる工程を
足すことになるので、その方針変更の是非を含めて計画が要る。

**判定箇所（file:line）**

- `src/results.rs:66` `ResultFile::of` — 先頭のキーワードで結果ファイルを決める。`DROP` は
  既定の `Self::Text`（`<id>.txt`）に落ちる。ここはファイル名を決めるだけで、中身は決めない
- `src/operation/execution.rs:243-268` `write_result` — 本体（`to_text` の結果）を置き、
  `outcome.columns` が空でなければ `.metadata` を置く。`execution.rs:264` のコメントに
  「DROP TABLE だけは本物が列なしの 41 バイトを置くが、athena-local は置かない」とある
- `src/operation/classification.rs` — `StatementType` / `SubstatementType`。`DROP_TABLE` の
  判定が既にある（`classification.rs:132`）ので、文の種類の判定はここから取れる
- `src/metadata.rs` — 41B の中身（クエリ ID + `updateType`）はここがそのまま組み立てられる。
  列が無くても書ける形かどうかの確認が要る
- `src/convert/result_set.rs:119` — 「Trino は CREATE TABLE / DROP TABLE に columns: [] を返す」
  というコメント。本物は列 0 個なのに空の行を 2 つ返し、連結すると改行 1 つになる

**共有できる既存機構**

- テーブルの形式を Trino に聞く経路はまだ無い。`src/trino.rs` の `syntax_error` が
  「本編とは別のクエリを投げる」前例（`PREPARE athena_local_syntax_check FROM ...`）で、
  同じ形で `SHOW CREATE TABLE` か `$properties` / `information_schema` を投げられる
- `src/catalog.rs` の `skip_leading_trivia` が先頭の空白とコメントの読み飛ばしを持っている。
  DROP の対象テーブル名を SQL から取り出すなら、ここから始めることになる

**原因の仮説**

本物の Athena は Iceberg のテーブルへの `DROP TABLE` だけをクエリエンジン側で処理し、
列 0 個で空の行を 2 つ返す（= 連結して改行 1 つ）うえ、`updateType` を持つので
`.metadata` を置く。Hive の `DROP TABLE` は Hive 側で処理され、行も `updateType` も
持たない。README の「失敗したクエリが結果ファイルを置くかどうかも Hive とクエリエンジンで
割れる」という既知の分かれ方（README の Caveats）と同じ境界に見える。**未検証**。

**未実測・未確認の一覧**

- 上の「未実測のまま残るもの」5 項目（2 ラウンド目で埋まる）
- Trino 側で、`DROP TABLE` の対象がどの形式かを事前に知る手段があるか（`SHOW CREATE TABLE`
  は DROP 済みのテーブルには使えないので、DROP の**前**に投げる必要がある）。対象が存在
  しない `DROP TABLE IF EXISTS` のときにどうするかも決まっていない
- 修飾名の解決（カタログ・スキーマの既定、`TRINO_CATALOG_MAP` の別名）を経た後のテーブル名で
  問い合わせる必要があるか
- `5.md:339` の決定「列が無ければ `.metadata` を置かない」を覆すことになるので、その
  dismissed の前提（JDBC 3.8.1 は欠落を INFO で流す／3.5.1 未満は列の無い DDL 全般で
  NoSuchKey になる）が今も成り立つか
