## 設計判断

統括役の仮決め（Plan と計画レビューで反証されなければ確定。Step 6b で提示）:

1. **toolbox 内の `$HOME` は `<repo>/.toolbox/home`**。理由: jdbc-drivers/lib.sh:190 が `$HOME/.cache/athena-local-jdbc` の jar を `docker compose run -v` の元に渡し、デーモンはホストのパスで解決する。リポジトリをホストと同じ絶対パスにマウントするので、その配下ならホストと toolbox で同じパスに実在する。python の venv もここに bookworm の python で作り直す（ホストの linuxbrew 製 venv は流用しない）。
2. **`CARGO_HOME=<repo>/.toolbox/cargo`**、PATH は `/usr/local/cargo/bin` のまま。
3. **`CARGO_TARGET_DIR=<repo>/.toolbox/target`** を dev.sh が export し、足場の `$REPO_ROOT/target/release/athena-local` の直書きを `BINARY="${CARGO_TARGET_DIR:-$REPO_ROOT/target}/release/athena-local"` に変える。理由（Plan の反証で差し替え）: ホスト製バイナリは GLIBC_2.34 までしか要求せず bookworm でも動く（readelf で実測）ので、`target/` を共有すると「toolbox でビルドしたのに古いホスト製バイナリが黙って使われる」（minio/verify.sh:157 でビルド、:185 で起動）。分けたうえで起動パスを揃えないと、ビルド先と起動元が食い違う。tools/measure の jdbc-metadata.sh:235,266 と jdbc-show-metadata.sh:240,271 も同じ形なので今回一緒に直す（grep の守りを tools/ 全体に広げる）。retention-stress.sh:15（debug、cwd 相対）は 2 段階目。「`.toolbox/target` を `<repo>/target` に被せる」案は、ホストと toolbox でパスの意味が違う場所を 1 つ作るので採らない。
4. **ホストの `/tmp` を toolbox の `/tmp` に同じパスでバインド**。理由: 9 本の足場が証跡を `/tmp/athena-local-issueNN-*` に直書きしてパスを表示する。共有すれば decisions.md:14 の判断もそのまま真。
5. **`compose.yml`（ルート、`name: athena-local`）の `dev` サービスとして定義し、`tools/dev.sh` は `docker compose -f <repo>/compose.yml run --rm dev env -- "$@"` の薄い包みにする**（#126 の方針。段階 2 で trino / minio を同じファイルに足す）。`dev` は段階 1 では `network_mode: host`（足場は無改造で `127.0.0.1:<port>` を使い続ける）、`init: true`（bash が PID 1 で SIGINT を無視し trap の後始末が走らなくなるのを防ぐ）、`user: "${DEV_UID}:${DEV_GID}"`、`group_add: ["${DOCKER_GID}"]`（`compose run` に `--group-add` は無い。yml の `group_add:` が効くことを実測）、`working_dir: ${DEV_CWD}`、`environment:` に HOME / CARGO_HOME / CARGO_TARGET_DIR（`${DEV_REPO}/.toolbox/...`）と USER / LOGNAME（passwd に uid 1000 の行が無く `getpass.getuser()` が落ちるのを実測）、`volumes:` に `${DEV_REPO}:${DEV_REPO}`、`/tmp:/tmp`、`/var/run/docker.sock:/var/run/docker.sock`。dev.sh はこれらの変数を export してから compose を呼ぶ。compose.yml 側は素の `${DEV_CWD}` で受ける（`:?` は使わないサービスの補間エラーでも compose 全体を止めるので、段階 2 で足場が toolbox の中から `compose up/down trino` を呼べなくなる。再レビューで実測）。dev.sh は `DOCKER_GID=$(stat ...)` と代入してから export する 2 行に分け、`set -e` で止める。`$CWD` がリポジトリ外なら中止。**TTY の分岐は置かない**（compose が stdin と stdout がともに端末のときだけ TTY を割り当てるのを実測。stdin がパイプなら `-T` 無しで `echo 1 | ... cat` が `1` を返す）。事前の mkdir は `.toolbox/home` だけ（cargo と target は cargo が自分で作る）。**`~/.aws` のマウントと awscli v2 は段階 3**（e2e は aws を呼ばず `~/.aws` も読まない。ホストの `~/.aws` は空。CLAUDE.md の注意書きは「足場は aws を使わない」と書けば済む）。
6. イメージのタグは Dockerfile の sha256 先頭 12 桁（`TOOLBOX_TAG`）。compose.yml は `image: athena-local-toolbox:${TOOLBOX_TAG}`、`build: { context: tools/toolbox }`、**`pull_policy: never`** を持つ。手元にタグが無ければ `docker compose run` が pull を試みずにそのまま build に落ちる（実測。既定の pull policy だと存在しない `docker.io/library/athena-local-toolbox` への pull で失敗してから build に進む）。**dev.sh に inspect / build の分岐は置かない**。Dockerfile を変えればタグが変わり、次の run で作り直される。

Dockerfile の層: `FROM rust:1.98-bookworm`（ルートの Dockerfile:2 と揃える相互参照コメント）→ `rustup component add clippy rustfmt` → apt（jq python3-venv python3-pip python3-boto3 uuid-runtime iproute2 openssl ca-certificates curl gnupg）→ Docker 公式 apt（keyring + `dpkg --print-architecture`）で docker-ce-cli docker-compose-plugin。USER と ENTRYPOINT は置かない。awscli は 2 段階目。

dev.sh の擬似コード:
```
set -euo pipefail
die(msg): stderr に "dev.sh: msg"、exit 2
main:
  [ $# -ge 1 ] || die usage
  REPO=$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd -P); CWD=$(pwd -P)
  case "$CWD/" in "$REPO/"*) ;; *) die リポジトリの外 ;; esac
  DOCKER_GID=$(stat -c %g /var/run/docker.sock)      # 無ければ set -e で止まる（代入と export を分ける）
  TOOLBOX_TAG=$(sha256sum "$REPO/tools/toolbox/Dockerfile" | cut -c1-12)
  export DEV_REPO=$REPO DEV_CWD=$CWD DEV_UID=$(id -u) DEV_GID=$(id -g) DEV_USER=$(id -un) DOCKER_GID TOOLBOX_TAG
  mkdir -p "$REPO/.toolbox/home"
  exec docker compose -f "$REPO/compose.yml" run --rm dev env -- "$@"
```
分岐 2 つ: 引数無し（usage）/ cwd が外。ソケット無しは `stat` の失敗で `set -e` が止める。image の有無と TTY は compose に任せる（実測済み）。AWS の資格情報 6 変数の受け渡しは段階 3 に送る（e2e は読まない）。

compose.yml（段階 1）:
```yaml
name: athena-local
services:
  dev:
    image: athena-local-toolbox:${TOOLBOX_TAG}
    build: { context: tools/toolbox }
    pull_policy: never
    network_mode: host
    init: true
    user: "${DEV_UID}:${DEV_GID}"
    group_add: ["${DOCKER_GID}"]
```

### 直列化・正規化境界
- docker の引数は配列に積み `exec docker "${ARGS[@]}" "$TAG" env -- "$@"`。シェルを挟まず手書きの引用はしない。厄介な入力: `tools/dev.sh printf '<%s>\n' 'a b' "c'd" '$HOME' ''` が 4 行 `<a b>` `<c'd>` `<$HOME>` `<>`。`~` はホストで展開される（文書に書く）。

- `env -- NAME=VALUE cmd` が代入として効くこと（表 4b で `a b` を確認済み）。
