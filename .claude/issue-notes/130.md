## 事前に確認した事実

- `.github/workflows/ci.yml`: `check` ジョブ 1 つ（ubuntu-24.04、ホストで `rustup component add` → `Swatinem/rust-cache@v2` → fmt / clippy / test）。トリガは main への push、pull_request、workflow_dispatch。e2e は走っていない。
- `.github/workflows/docker.yml`: `docker/setup-buildx-action@v4` と `docker/build-push-action@v7` の `cache-from/to: type=gha,scope=...` を使っている（リポジトリの前例）。
- `tools/dev.sh`: `stat -c %g /var/run/docker.sock`、`id -u/-g/-un`、`DEV_HOST_HOME=$HOME`、タグは `sha256sum tools/toolbox/Dockerfile | cut -c1-12`、`exec docker compose -f compose.yml run --rm --use-aliases dev env -- "$@"`。compose.yml の dev は `pull_policy: never` で、手元に `athena-local-toolbox:<タグ>` が無ければ build する。
- request-errors: docker も Trino も使わない（verify.sh:9）。`cargo build --release --locked`（:135）。SKIP_BUILD=1 で省略できる。
- paging-validation: `SERVICES=(trino)`（:39）。`trinodb/trino:482` の pull が要る。
- toolbox の中の cargo の成果物は `.toolbox/cargo`（レジストリ）と `.toolbox/target`。

## 設計判断

1. **別ジョブ `e2e` を足し、`check` は変えない**（ホストで直に cargo のまま。issue は e2e を足すことだけ求める）。
2. **toolbox のイメージは GHA キャッシュ（`mode` は既定の min）。Docker Hub には docker.yml と同じ secrets でログインする（匿名 pull の制限を避ける。secrets が無いときは省く）**。イメージは（docker.yml と同じ `type=gha`。Docker Hub には置かない＝シークレット不要、公開イメージを増やさない）。`docker/build-push-action` で `context: tools/toolbox`、`load: true`、`tags: athena-local-toolbox:<タグ>` として手元に置けば、`tools/dev.sh` の `docker compose run` はイメージがあるので build しない。タグは dev.sh と同じ `sha256sum tools/toolbox/Dockerfile | cut -c1-12` で計算する（ずれても compose が build に落ちるだけで壊れない）。
3. **cargo の成果物は `actions/cache` で `.toolbox/cargo/registry` と `.toolbox/target/release` だけ**（キーは Cargo.lock のハッシュと toolbox のタグ。debug まで入れると数 GB で GHA キャッシュの 10GB を docker.yml と取り合う）。
4. **足場は request-errors と paging-validation の 2 本**（issue の「余力があれば」を採る。paging は Trino の pull だけで MinIO は要らない）。2 本目は `SKIP_BUILD=1`（1 本目のビルドを使う）。retention と jdbc-drivers は載せない（issue どおり）。
5. 失敗時の証跡（`/tmp/athena-local-issue*`）はアーティファクトに上げない（各足場は結果表を標準出力に出すので Actions のログで足りる。削減）。
6. 文書: CLAUDE.md の CI の一文、development.md の CI の記述、decisions.md に 1 箇条（GHA キャッシュの理由）。CHANGELOG は触らない。

## 計画

1 フェーズ（実装は自分。小規模の経路・本番コード 0 行、YAML 約 40 行、文書 数行）。

- `.github/workflows/ci.yml` に `e2e` ジョブ: checkout → setup-buildx → タグの計算（`$GITHUB_OUTPUT`）→ build-push-action（load、GHA キャッシュ、scope=toolbox）→ actions/cache（.toolbox の cargo と target）→ `tools/dev.sh tools/e2e/request-errors/verify.sh` → `tools/dev.sh SKIP_BUILD=1 tools/e2e/paging-validation/verify.sh`。
- 検証: (1) 手元で同じ手順（`docker buildx build --load -t athena-local-toolbox:<タグ> tools/toolbox` のあと `tools/dev.sh true` の stderr に `Building` が出ない）、(2) PR の CI で `e2e` ジョブが成功（受け入れ条件）、(3) 2 回目の CI（push を積んだとき）でイメージのビルドがキャッシュから来る（ログに `CACHED`）。
- 壊す候補: タグの計算を変えると compose が build に落ちる（壊れず遅くなるだけ）ことを手元で見る。足場の verify.sh の終了コードが FAIL 件数なので、CI は FAIL 1 件でも赤になる（既存の契約）。
- 人間検証: 無し（CI の実行が検証そのもの）。#131 の amd64 のビルドは、この CI（ubuntu-24.04 は amd64）で toolbox のイメージがビルドされれば埋まる。
