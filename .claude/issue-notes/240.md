## 事前に確認した事実
### 過去の実測（調査 3）
1. 末尾の `;` だけの SELECT（#228 の k6〜k12・k28、#76 の g2-semicolon）はすべて SUCCEEDED・DML/SELECT・`.csv`。GetQueryExecution の `Query` は末尾の `;` を前後の空白・改行・CR・続く `;` ごと落とした形: `SELECT 1;;`・`SELECT 1; ;`・`SELECT 1; `・`SELECT 1;\n\n`・`SELECT 1 ;`・`SELECT 1;\r\n` → `SELECT 1`、`-- c\nSELECT 1;` → `-- c\nSELECT 1`、`SELECT 1 -- c\n;` → `SELECT 1 -- c`
2. g2-semicolon の `.csv`（12 バイト、binary/octet-stream）と `.metadata`（81 バイト）は `SELECT 1` とバイト列が同じ（QueryExecutionId 由来の差だけ）
3. `CREATE TABLE <db>.<t> (n int);`（k27）は `;` の無い形と同じ No location
4. 未測定: 先頭の `;`、`SELECT;`、`DESCRIBE <無い表>;`、S3 Tables の Context の 2 catalogs に `;`、`(n int NOT NULL);` の NV、`SHOW TABLES;`、CTAS・INSERT・EXPLAIN の末尾 `;`、`SELECT ?;`（パラメータ付き）。`;` の無い文の末尾の空白が `Query` で落ちるかも未測定

## 実測の結果
ROUND=7（run-20260926-040524、L 群 29 項目）と #228 の ROUND=6（run-20260926-033720）。表は docs/dev/measurements/statements.md の「末尾の `;` だけの文と前後の空白（#240）」。
- 決め手: 本物は `;`（引用符とコメントの外）で区切り、空白だけでない片がちょうど 1 つなら、その片の**前後の空白を落とした文**を「文」として使う。GetQueryExecution の Query・構文エラーの位置と文言・文を引用する文言（2 catalogs）はすべてこの文で決まる。`;` の無い文でも前後の空白は落ちる（l2・l3）。先頭の `;` も通る（l6・l7）
- 空白だけでない片が 0（`;` だけ）→ `Empty sql statement: ;`（MALFORMED_QUERY。l8）。2 以上 → Only one（#228）
- 冪等の比較は受け取ったままの文（`SELECT 1;` の後に同じトークンで `SELECT 1`・`SELECT 1;;`・`SELECT 1 ` → Idempotent parameters do not match。l22〜l26）
- 文の種類・出力先（SHOW TABLES;・EXPLAIN;・CTAS;・INSERT;・SHOW CREATE TABLE;・DROP;・`SELECT ?;`）は `;` の無い形と同じ。`DESCRIBE <db>.<t>;` の Query は `DESCRIBE <t>`（DB 名が落ちた。l18。範囲外）
- `SELECT 1\nFROM;` → `Queries of this type are not supported`（INVALID_INPUT。l10）。`;` の無い `SELECT * FROM` と同じ既知の差（caveats.md:38）

## 設計判断
- D2（実測 l2・l3 から）: 正規化は `;` の有無によらず前後の空白（空白・タブ・CR・LF）を落とす。本物の Query がそうなっている
- D3（実測 l22〜l26 から）: 冪等の指紋（Fingerprint.query）は受け取ったままの文で作る
- D4（実測 l8 から）: 空白だけでない片が 0 で `;` があるときは `Empty sql statement: <末尾の空白を落とした受け取った文>`（MALFORMED_QUERY）。`;` が無い空白だけの文は今までどおり（未実測）
- D1（ユーザーの判断、13:03）: 入口で正規化する（案 A）。StartQueryExecution の入口で、末尾の `;` がある文だけを「最初の `;` の手前まで・末尾の空白を落とした文」にし、Query・判定・構文チェック・実行のすべてに使う。本物の Query の見え方（`;` と前後の空白が落ちる）と一致し、`Cursor::at_end` に頼る 2 判定（`content_type::is_literal_only_select`・`unquoted_ddl/create_table::after_columns`）を直さずに済む。decisions.md (4)「Query は受け取ったまま」に「本物が正規化する場合」の例外を足す。案 B（実行の中だけで切り、Query は受け取ったまま）は本物の Query と食い違うので採らない

### フェーズ 1: 入口で文を正規化する（本番 約 40 行）
- ファイル構成: `src/operation/execution.rs`（389 → 約 400 行。`multiple_statements` を `statement` に置き換え、入口の配線を変える）。新規ファイル無し。athena-sql は変えない（`statements` を再利用）
- `fn statement(sql: &str) -> Result<&str, String>`（execution.rs、#228 の `multiple_statements` の置き換え）:
  - `athena_sql::statements(sql)` の片のうち空白（空白・タブ・CR・LF）だけでないものを数える
  - 2 以上 → Err(`Only one sql statement is allowed. Got: <sql の末尾の空白を落としたもの>`)（#228 のまま）
  - 0 で片が 2 以上（`;` がある）→ Err(`Empty sql statement: <sql の末尾の空白を落としたもの>`)（D4）
  - 0 で `;` が無い → Ok(sql)（今までどおり。空白だけの文は未実測）
  - 1 → Ok(その片.trim_matches(空白))（D2。`;` が無ければ片は sql そのもの）
- 入口の配線（start_query_execution）: トークン → `context_defaults`（指紋は受け取ったまま。D3）→ `statement` を求める → `result_location`（正規化した文。Err なら受け取った文）→ Err なら MALFORMED_QUERY で返す（#228 と同じ位置）→ 以降の `syntax_error`・`context_catalog::resolve`・`entity_check::check`・`quoted_names`・`unquoted_ddl`・`create_table_catalog::check`・`Submission.query` はすべて正規化した文
- 依拠する前提表:
  | 前提 | 破らないか | 保証元 |
