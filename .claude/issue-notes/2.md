## 計画レビューの結果（Step 6、2026-09-16）

Explore 3 本（契約・呼び出し元／再利用・一貫性・構造／削減）。

**採用 1（構造）: `src/workgroup.rs` を新設しない。**

自分でも grep して裏を取った。`App` を触るファイルは `handler.rs`・`lib.rs`・`operation.rs` の 3 つだけで、`-> Response` を返すのも `handler.rs`・`operation.rs`・`response.rs` だけ。`catalog.rs`／`statement.rs`／`failure.rs`／`results.rs`／`convert.rs`／`store.rs`／`trino.rs`／`config.rs` はどれも `App` を受け取らず `Response` も返さない。**このリポジトリの分割軸は「Store/Trino を叩くかどうか」ではなく、「`App`/`Response` を扱うディスパッチ本体（`operation.rs` に集約）」と「それが呼ぶロジックの塊（各ヘルパ）」だった。** 「Trino を叩かないから分ける」という理由は既存コードに当てはめると破綻する（`get_query_execution` と `stop_query_execution` も Trino を叩かない）。行数の理由も弱い（`operation.rs` 566 行に対し `convert.rs` は 863 行）。これで新規ファイルと `mod` 宣言と `use` 行がまとめて消えた。

**採用 2（テスト）: ミューテーション候補の「`app.trino` や `app.store` を呼ぶ」を 2 行に分ける。**

`trino_には一切問い合わせない` で検知できるのは `app.trino` だけ。`Store` は本物が使われ、呼ばれたかを外から観測できない。1 つの検知手段に 2 つのミューテーションを押し込めていた。Store を計測する足場は足さない（本来触らない設計で、そのための機構は過剰）。

**採用 3（契約、最重要）: `GetWorkGroup` を実装すると、awswrangler が実 AWS を叩くようになる。**

指摘を鵜呑みにせず、スクラッチパッドの awswrangler 3.17.1 の実ソースを自分で読んで全リンクを確認した。

- **今塞がっている理由（偶然の防波堤）**: `read_sql_query` は既定が `s3_output=None`・`workgroup="primary"`（`_read.py:951-975`）なので必ず `GetWorkGroup` を呼ぶ。`get_work_group` は `try_it(ex_code="ThrottlingException")` で包まれているだけ（`_utils.py:1121-1129`）なので、それ以外の `ClientError` はそのまま上がる。今の athena-local は 400 を返す（`src/handler.rs:39`）ため、ここで止まる。
- **実装後に開く経路**: `_get_s3_output`（`_utils.py:68-86`）は、呼び出し側の `s3_output` もワークグループの `OutputLocation` も無いとき `create_athena_bucket()` を呼ぶ。これは `sts.get_account_id()`（`:487`）と S3 クライアントを使う**本物の AWS への発信**。
- **到達経路は閉じて数えた**: `create_athena_bucket` の呼び出し元は `_get_s3_output` ただ 1 つ。その `_get_s3_output` の呼び出し元は 2 つだけ。

| 呼び出し元 | 守られているか |
| --- | --- |
| `_read.py:602`（`_resolve_query_without_cache_regular`。`ctas_approach=False`） | `if not wg_config.managed_results:` で守られている |
| `_read.py:775`（`_unload`。`unload_approach=True`） | **守られていない** |

`_resolve_query_without_cache_ctas`（`:468`）は `s3_output` を受け取って渡すだけで `_get_s3_output` を呼ばない。**既定の `ctas_approach=True` はこの経路に入らない。** 公開 API の `wr.athena.start_query_execution` は `_utils.py:105` の guard で守られている。

- **`EnforceWorkGroupConfiguration` の真偽は影響しない。** `_get_s3_output` の 1 番目の分岐は `enforced and s3_output is not None` なので、出力先が無ければ真偽どちらでも同じフォールバックに落ちる。
- **対応は判断 4 のとおり README のみ。** 計画にあった「`ATHENA_LOCAL_OUTPUT_LOCATION` が無いと `NO_OUTPUT_LOCATION` になる」という記述は**誤り**（その手前で実 AWS を叩く）なので削除した。
