## 実測の結果（2026-09-21）

**結論: 列を 1 つも持たない `.metadata`（41 バイト / 38 バイト）を Athena JDBC 3.8.1 は例外なく読む。#39 の実装を見直す必要は無い。**

| # | 文 | `.metadata` | ドライバのログ | 結果 |
|---|---|---|---|---|
| 1 | `DROP TABLE`（Iceberg） | 41 バイト（列 0 個） | `loaded query result metadata from "...txt.metadata"` | 例外なし。`hasResultSet=false updateCount=0` |
| 2 | `ALTER TABLE ... ADD COLUMN`（Hive） | 38 バイト（列 0 個） | `loaded query result metadata from "...txt.metadata"` | 例外なし。`hasResultSet=false updateCount=0` |
| 3 | `DROP TABLE`（Hive。対照） | 無し | `does not have query result metadata` | 例外なし（`5.md` の先行知見と一致） |
| 4 | `SELECT 1 AS n`（回帰） | 81 バイト | `loaded ...csv.metadata` | `columnCount=1`、`rows=1` |

`ResultFetcher` は**既定（auto）と `S3` の明示の両方**で同じ 4 ケースを流し、どちらも `failures=0`。
nginx のアクセスログで `.metadata` への GET が 13 件あり、ドライバが S3 を直接読んだことを裏付けた。

回収した `.metadata` の中身（`od`）も issue の記述と一致した:

リスクの見積もり（#39 の「壊れる可能性は低い」）は当たっていた。`.metadata` を**置かない**ときの
先行知見（`5.md`: 404 を INFO で流して続行）に加えて、**置いたときも列 0 個で問題ない**ことが確定した。

## ドライバの入手（issue の最大のブロッカーが解けた）

issue は「ドライバが手に入らない」で止まっていた。**取れた。**

```
https://downloads.athena.us-east-1.amazonaws.com/drivers/JDBC/3.8.1/athena-jdbc-3.8.1-with-dependencies.jar
```

HTTP 200、43,763,083 バイト。`META-INF/services/java.sql.Driver` = `com.amazon.athena.jdbc.AthenaDriver`、
`com/amazon/athena/jdbc/support/EndpointHelper.class` あり（README:166 が言及する本物）。

Maven Central に無いのは issue の記述どおりで、そこにある `com.amazonaws:athena-jdbc`（calver）は
Athena Federated Query の JDBC コネクタ。`java.sql.Driver` を持たないので `No suitable driver found` になる。
`pom.xml` からはこの誤った依存を外し、ドライバは実測スクリプトが取得してコンテナにマウントする形にした
（`Main.java` は `java.sql` しか使わず、ドライバは実行時に `ServiceLoader` が拾うので、Maven の依存にしなくてよい）。

## 実測の経緯（4 ラウンド。measurement.md「3 を超えたら振り返る」）

| ラウンド | 変えた条件 | 結果 |
|---|---|---|
| 1 | 初回 | `No suitable driver found`。ドライバ jar を `target/dependency/` に置けなかった（maven コンテナが root で作るのでホストから書けない） |
| 2 | jar をコンテナに直接マウント | 接続まで進み `UnknownHostException: tls-proxy`。`getent hosts` も `java.net.InetAddress` も解決できるのに、ドライバが内包する AWS SDK だけが失敗した |
| 3 | `/etc/hosts` に IP を固定 | `NoSuchBucketException`。ドライバの S3 クライアントが virtual-hosted style（`athena-results.tls-proxy`）でアクセスしていた |
| 4 | MinIO に `MINIO_DOMAIN: tls-proxy` | **全ケース PASS** |

**振り返り（要件 1「疎通 preflight」を外していた）**: preflight がコマンドの有無しか見ておらず、
「ドライバが classpath に載るか」「ドライバが依存先に到達できるか」という**本当の疎通**を見ていなかった。
最初に `SELECT 1` を 1 本だけ JDBC で流す preflight を置いていれば、ラウンド 1〜3 は 1 ラウンドに畳めた。
外部クライアント（ドライバ・SDK）を相手にする実測では、**そのクライアント自身で最小の 1 本を通すことが preflight**。

ラウンド 2 と 3 は、条件を 1 つだけ変えた対照になっている（2→3 は `/etc/hosts` だけ、3→4 は `MINIO_DOMAIN` だけ）。
README に書いた 2 つの必須条件は、この対照がそのまま根拠。

## 副産物（README に反映した）

- **`MINIO_DOMAIN` が要る**: ドライバの S3 クライアントは virtual-hosted style でバケットを指す。
  README:162 に「MinIO needs `MINIO_DOMAIN` set to the same domain」と書いてあったが、
  足場の compose には設定が無かった。実測で必要性が裏付けられたので compose に足した
- **コンテナ内では `/etc/hosts` に固定が要る**: ドライバが内包する AWS SDK は、Docker の埋め込みリゾルバ
  （`/etc/resolv.conf` の `search .`、`ndots:0`）が返す名前を `UnknownHostException` にする。
  同じコンテナで `getent hosts` と `java.net.InetAddress.getByName` はどちらも解決できるので、SDK 側の DNS 実装の問題
- ドライバは `jdbc:awsathena://` を deprecated と警告する（`jdbc:athena://` を推奨）
- 非標準ポート（8443）の `AthenaEndpoint` では streaming endpoint を自動構築しない（警告 1 行。動作に支障なし）
