## 実測の結果（ラウンド 3・4 の統合。NV = no viable alternative、MM = mismatched input … expecting {#204 の一覧}）
- ALTER TABLE: 3 部の 2 番目（と 2・3 番目）が引用符付きも一般の規則 NV(文の最初の語 … 引用符付きの部分 @ その部分)
- 4 部以上（5 部も）の DESCRIBE・DESC・SHOW COLUMNS FROM／IN: 引用符の有無・位置によらず `Invalid table name <各部の value() を . でつないだもの>`（MALFORMED_QUERY）。`AwsDataCatalog…N` は小文字、`"a""b"`→`a"b`、`"x.y"`→`x.y`。1 部目が S3 Tables の別名でもこちらが先
- 4 部以上の DROP TABLE（IF EXISTS も）・ALTER TABLE: 引用符付きの部分が 1〜3 部目にあれば 3 部の規則（DROP: p1 MM、p2 NV(名前の始まり…)、p3 MM ／ ALTER: NV(文の最初の語…)）。無引用・4 部目以降だけなら 3 つ目の `.` の位置で、DROP は `line L:C: mismatched input '.' expecting {<EOF>, 'PURGE'}`、ALTER は `line L:C: no viable alternative at input '<文の最初の語から 3 つ目の . まで>'`
- SHOW TABLES IN の 2 部: 無引用は SUCCEEDED、引用符付きは最初の引用符付きの部分で MM
- CTAS でない CREATE TABLE の 2・3 部: NV(文の最初の語 … 最初の引用符付きの部分 @ その部分)。`CREATE TABLE IF NOT EXISTS "t" (n int)` は `line 1:28: no viable alternative at input 'CREATE TABLE IF NOT EXISTS "t"'`。無引用は `No location was specified…`（範囲外・caveats 既載）
- 非 ASCII: DROP・ALTER・SHOW CREATE TABLE・SHOW TABLES IN・CREATE TABLE は一般の規則どおり（実在しない "日本" でも）
- DESCRIBE・DESC・SHOW COLUMNS の存在の確認（Glue、開始時）: テーブル不在（1・2・3 部、無引用・引用符付き、非 ASCII）・スキーマ不在・文脈の Database 不在はすべて `Entity Not Found (Service: AmazonDataCatalog; Status Code: 400; Error Code: EntityNotFoundException; Request ID: <毎回違う UUID>; Proxy: null)`、INVALID_INPUT。大文字の無引用 `T`・`DB.T` は SUCCEEDED。実在する非 ASCII 名は構文の文言
- カタログ不在の 3 部（`nocatalog_204.db.t`）: `Catalog 'nocatalog_204' does not exist`、DATACATALOG_NOT_FOUND（DESCRIBE・SHOW COLUMNS）
- ビュー: `DESCRIBE v`・`DESCRIBE "v"`・`SHOW COLUMNS FROM v`・`SHOW COLUMNS FROM "v"` はすべて SUCCEEDED（DESC_VIEW）→ **引用符付きの名前の構文の文言はテーブルだけ**。今の athena-local は `DESCRIBE "v"` を弾いている（本物との差）
- S3 Tables（対照 SELECT が通る状態）: DESCRIBE・DESC・SHOW COLUMNS・実在しない表への DESCRIBE は 2 catalogs、SHOW CREATE TABLE は not supported、DROP は MM(p1)、ALTER は NV → ラウンド 1・2 と同じ
- `ALTER TABLE IF EXISTS "t"`（ラウンド 2 の u2-ifq を読み直し）: 無引用と同じ文言で、範囲外の差（caveats 既載）
- 判定の順序（DESCRIBE・SHOW COLUMNS）: Trino の構文エラー → 4 部以上 → S3 Tables の別名 → カタログ不在 → テーブル不在 → ビューなら実行 → テーブルで引用符付きなら構文の文言

## 設計判断
1. 存在の確認まで今回実装する（ユーザーの判断、2026-09-25）。#204 の「非 ASCII は弾かない」は撤回
2. 存在の確認は既存の `table_format::probe_sql` をそのまま使う（1 問い合わせでカタログ有無・テーブル有無・ビューが決まる。事実 8）。新しい SQL を作らないので一致台帳（テストの probe_sql の写し）も増えない。応答の読み分けは新しい関数（2 列・1 行の形でなければ不確定）
3. 探索に渡すスキーマ・テーブルは小文字にする（事実 8。本物は大文字の名前も見つける）。カタログは `config.trino_catalog` で別名を解決した値
4. 不確定（Trino の失敗・応答の形が違う・カタログ／スキーマが決まらない）なら存在の確認では弾かず、テーブルとして扱う（引用符付きなら #204 の文言、無引用なら実行）＝今までどおり
5. カタログ不在の文言（DATACATALOG_NOT_FOUND）は、名前にカタログを書いた 3 部の形だけで返す。文脈・既定のカタログが Trino に無いときは不確定と同じ扱い（未実測）
6. quoted_names は純関数のまま、戻り値も変えない。存在の確認（新モジュール）は 3 択を返す: 弾く（カタログ不在・テーブル不在）／実行へ進む（ビュー。quoted_names を呼ばない）／続ける（対象外・4 部以上・別名・テーブル・不確定。quoted_names を今までどおり呼ぶ）。4 部以上は parse_target_table が None、別名は探索しないので、判定の順序（4 部 → 別名 → カタログ → 存在 → ビュー → 構文）は保たれる（Plan の追補の案を採用）
7. `table_name_start` は変えない（事実 3）
8. 開始時と実行時（format_probe）で同じ探索が 2 回走るのは受け入れる（持ち越しは Store の構造変更になる）
