## 事前に確認した事実

Explore 1 本（opus、8 項目）から転記。落とした番号: 7（関数一覧。計画に要る分だけ下に）、8（CHANGELOG の現状）。

1. 入口は `render.rs:11-26` の `to_var_char_value`。トップレベルの varbinary は :14-16 で `scalar::varbinary` に。複合型は `ValueType::parse` → 再帰の `render`（:29-69）。**複合型の中の varbinary は :32 の 1 腕** `(ValueType::Varbinary, Value::String(text)) => super::scalar::varbinary(text)`。array :35-37、map :40-53（キーは :50 で JSON のキーのまま）、row :54-65。ネストも同じ腕に届く
2. `scalar::varbinary`（scalar.rs:59-69）は自前の `decode_base64`（:71-97）で base64 → `01 02`、読めなければそのまま。トップレベルと複合型の中で同じ関数
3. テスト: render.rs:180 `varbinary_は_16_進を_空白で区切る`（トップレベル。`"AQI="`→`01 02`、`"/+8="`→`ff ef`、`""`→`""`、非 base64 はそのまま）、**render.rs:195 `配列の中の_varbinary_も_16_進にする`**（`["AQI=",null]` → `[01 02, null]`）。map・row・ネストのテストは無い。results/tests.rs:65-102 はトップレベルの CSV/txt。`tests/` に varbinary は 0 件
4. docs: `docs/caveats.md:160` `## Value rendering`、:162-164「The same form is used inside composite values, which was not measured.」。measurements/result-files.md:492-510（値の表記。x2 の 4 値 `2545d692`・`2635f945`・`783cdbdf`・`4930b8c`＝8・8・8・7 桁。:510「実行ごとに変わるかは生データに無い」）
5. Trino は varbinary を base64 の文字列で送る（複合型の中でも。render.rs:198 の入力）。`raw_type` はトップレベルだけ、要素の型は `ValueType::parse` の再帰。CSV・txt・GetQueryResults はすべて `result_set.rs:29` → `to_var_char_value` を通る
6. Java の `byte[].toString()` は `[B@` + `Integer.toHexString(identityHashCode)`（先頭 0 無し、1〜8 桁。一般知識、未検証）。実測の 4 値の桁数と合う。同じ array の 2 要素も別の値
7. 未検証: map のキーが varbinary のとき（:50 で JSON のキーのまま）。Trino がどう送るかも未確認 → 触らない（範囲外）

## 設計判断

- Step 4（2026-09-24、ユーザー）: **本物の形に揃える**。複合型の中の varbinary は `[B@` + 16 進（先頭 0 無し、1〜8 桁）。本物の数字は identity hash で中身を表さず実行ごとに変わりうるが、athena-local はバイト列から決めた 32 ビットのハッシュ（FNV-1a）にして決定的にする（テストで固定できる。本物と「同じ値」にはならないが、本物自身も安定しない）。トップレベルは 16 進のまま（本物と同じ）
- ハッシュは FNV-1a 32 ビット（依存を足さない。`std` の `DefaultHasher` は版で変わりうるので使わない）。`{:x}` で先頭 0 を落とす（本物の 7 桁の値に合わせる）

### フェーズ 1: 複合型の中の varbinary を `[B@<fnv1a の 16 進>` にする（本番コード約 20 行、テスト約 25 行）
- `src/convert/scalar.rs`: `pub(super) fn nested_varbinary(text: &str) -> String` を `varbinary` の隣に足す。`decode_base64` で読めたバイト列の FNV-1a 32 ビットを `format!("[B@{hash:x}")`、読めなければ `varbinary` と同じく受け取ったまま。FNV-1a は 10 行の private fn（offset 0x811c9dc5、prime 0x01000193）。コメントに実測（2026-09-24、#146・#149）と「本物は identity hash で決定的でない」を書く
- `src/convert/render.rs:32`: `super::scalar::nested_varbinary(text)` に
- テスト（render.rs）: `配列の中の_varbinary_も_16_進にする`（:195）を `複合型の中の_varbinary_は_java_の_byte配列の_tostring_の形にする` に書き換え: array `["AQI=",null]` → `[[B@<h1>, null]`、map `{"k":"AQI="}` → `{k=[B@<h1>}`、row `["AQI="]`（`b varbinary`）→ `{b=[B@<h1>}`、違うバイト列（`"Aw=="`）は固定値で比べる（「違う値」の別アサーションと空バイト列の期待値は計画レビューで削った）。期待値の 16 進（FNV-1a 32 ビット、Python で計算）: `AQI=`（01 02）→ `ed74208a`、`Aw==`（03）→ `60c5eb2`（7 桁。先頭 0 が落ちる形の実例になる）、`""` → `811c9dc5`（offset そのもの）。トップレベルの :180 は変えない
- docs: `docs/caveats.md:162-164` を「トップレベルは `01 02`。複合型の中は本物が `[B@<hex>`（Java の byte[] の toString。中身を表さず値は安定しない）を返すので athena-local も `[B@` + バイト列から決めたハッシュにする（measured 2026-09-24）」に。CHANGELOG の Changed に 1 行
- 前提表: 複合型の中の varbinary は :32 の 1 腕にしか届かない（事実 1）／トップレベルは :14-16 で別経路（変えない）／`decode_base64` は既存（:71-97）
- ミューテーション: (a) :32 を `varbinary` に戻す → 新テストが落ちる (b) FNV の prime を変える → 期待値の 16 進が違って落ちる
- 先行できる作業: 無し。人間検証リスト: 無し。範囲外: map のキーが varbinary（事実 7）→ 触らない・起票しない（Trino の送り方も未確認で、本物でも未実測。unmeasured に載せるほどの用途が無い）
