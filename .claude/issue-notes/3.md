**変更対象**

- `src/athena.rs:6-21` `StartQueryExecutionRequest` に `ClientRequestToken` が**無い**。`deny_unknown_fields` はリポジトリ全体で 0 件なので、送られても serde が黙って捨てている。省略可の慣習は `#[serde(default)] pub x: Option<T>`。
- `src/operation.rs:34-85` の実際の順序: `parse` → catalog/database の既定 → **`Uuid::new_v4()`（`:48`。実行 ID の唯一の生成箇所）** → `result_location`（`:49-57`。`id` を S3 パスに使う）→ `syntax_error`（`:61-63`。Trino に `PREPARE` を投げる）→ work_group の既定 → `store.submit`（`:69-79`）→ `spawn_query`（`:80`）→ 応答。**構文エラーで弾かれた時点では Store に何も書かれていない。**
- `src/store.rs:13-16` `Store` は `executions: Arc<Mutex<HashMap<String, Execution>>>` の**単一フィールド・単一 Mutex**。`finish`（`:119-141`）と `cancel`（`:143-158`）は「1 回のロックの中で読み取り → 終端状態チェック → 書き込み」を完結させる流儀を徹底している（TOCTOU を避けるため）。
- **`Store::submit` の引数は `&self` 込みで既に 7 個**で clippy の `too_many_arguments` の上限ちょうど。増やすなら `Submission` に足す（先例 605d68c）。`src/store.rs` は `athena` を import していない。

### 主要な設計判断と根拠

- **フィンガープリントは `id` を焼き込む前の生のリクエスト値を比べる。中身は判断 5 の 3 つ: `query_string: String`、`database: Option<String>`、`output_location: Option<String>`。** `result_location()`（`operation.rs:89-119`）が作る `ResultLocation` は `id` を S3 キーに含む（`results.rs:99-107`）ため、`Execution.result_location` を比べると `id` の違いだけで常に不一致になる。database も既定を当てる前の値（`operation.rs:40-46`）を使う。既定は `Config` 由来の静的な値なので、同一プロセス内では判定結果は変わらない。`execution_parameters`（実測で比較されない）・`catalog`・`work_group`（未測定）は入れない。
- **`tokens` は `executions` と同じ 1 つの `Mutex` に同居させる。** 別 Mutex 2 本は「`tokens` を見て未登録 → `executions` に登録 → `tokens` に登録」の隙間に割り込まれ、同じトークンで 2 つの `Execution` ができる（TOCTOU）。`finish`（`store.rs:119-141`）と `cancel`（`store.rs:143-158`）が徹底している「1 ロック内で読み取り → 判定 → 書き込み」の流儀に合わせる。
- **対応表は `HashMap<String, Claim>`（token → { fingerprint, id }）で、フィンガープリントはここにだけ持つ。** `Execution` にトークンやフィンガープリントを足さない（既存フィールドと丸ごと重複し、`get()` の clone が増えるだけ。計画レビュー 採用 4）。`Execution` を線形探索する案は、`Store` に破棄の仕組みが無く `executions` が無期限に増える（issue の範囲外・`TODO.md:24-28`）ため不採用。
- **`submit` の明示引数は増やさず `Submission` に平フィールドで足す。** `Store::submit` は既に clippy の `too_many_arguments`（閾値 7）ちょうど。先例 605d68c。ラップ型（`Idempotency`）は作らない（採用 3）。
- **`Fingerprint` はプリミティブ（`String` / `Option<String>` / `Vec<String>`）だけで組み、`operation.rs` の既存の `Submission { .. }` リテラルの隣で組む。** `store.rs` が `athena.rs` に依存しない方針（`store.rs:62-64`）は、`Submission` と同じやり方で保てる。新モジュールは要らない（採用 5）。

### 並行性の設計（`submit` の 1 ロックだけ）

`submit(&self, id, submission) -> SubmitOutcome`。1 回のロックの中で `tokens.get(token)` を引き、(a) 無ければ `executions` と `tokens` の両方に登録して `Created`、(b) あってフィンガープリントが一致すれば何も作らず `Existing(既存の id)`、(c) あって一致しなければ `Conflict`。`operation.rs` は `Created` のときだけ `spawn_query` を呼ぶ。`Existing` は既存の id で応答、`Conflict` は実測したエラー。

**早期チェック（`match_token`）は置かない**（採用 6）。同時到着の解決は `submit` の 1 ロックで足り、逐次のリトライで増えるのは構文チェックの `PREPARE` 往復 1 回だけ。リトライはまれで、ローカルツールでその往復が問題になる根拠が無い。判定を 2 箇所に持つ方が「早期チェックは一致と言い、`submit` は不一致と言う」ずれを作れる。

**照合の位置は `submit`（`result_location` 検証と構文チェックの後）。** 本物がトークンの照合を構文チェックの前にするか後にするかは実測待ち（issue 本文）。観測できる差は「同じトークン・違うクエリ・そのクエリが構文エラー」のときにどちらのエラーが返るかだけ。実測で本物が照合を先にすると分かったら、そのときに位置を動かす。

### 正規化境界（判断 4: 正規化しない）

トークンは任意の文字列で `HashMap` のキーになる。空白・`"`・`\`・大文字がそのままワイヤに乗ることは実測済み（「事前に確認した事実」の表）。本物の正規化は未実測なので最小実装（何もしない）を既定にし、正規化が要ると分かったら `Store` に渡す直前の 1 箇所だけを直す。

| 観点 | 扱い |
| --- | --- |
| 大文字小文字 | 区別する |
| 前後の空白 | trim しない |
| 非 ASCII | そのまま |
| 空文字 | 「無し」とは区別する。`#[serde(default)]` はキーが無いときだけ `None` を埋めるので `""` は `Some("")`。**空文字を「無し」と同じエラーにするかは実測で決める** |
| 極端に長い | 検証しない（実測待ち） |

これらはどれも「コードに分岐を書かない」ことの確認なので、テストは **1 本のテーブル駆動**（大文字小文字違い・前後の空白違い・非 ASCII・極端に長い、の対を回して「同じ文字列なら同じ id、違えば別の id」）に畳む（採用 7）。
