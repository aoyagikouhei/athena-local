**未保証の前提**（別枠）

- 「モジュールをディレクトリ化しても `cargo fmt` / `clippy` の挙動が変わらない」はリポジトリのどのコードも保証していない。フェーズ1 のコミット前に 3 コマンドを実際に走らせて確かめる（この経路に実際に届く入力＝このリポジトリのソースそのものなので、走らせれば確定する）。

**テスト: 新しいテストは足さない**

挙動を変えない移動なので red→green の代わりに「既存テストが無変更で green」を根拠にする。成立する理由:

- src の 6 ユニットテストは対象 4 関数の入出力をアサートしており、定義がどのファイルにあるかに依存しない。テストコードも対象関数の中身も 1 文字も変えないので、green のままであることが「中身が変わっていない」の直接証拠になる。
- 実行系（`start_query_execution`〜`run`）の src ユニットテストは元々 0 本。この経路は `tests/` の 14 ファイル 3287 行（`idempotency.rs` 289 行・`dml.rs` 295 行・`parameters.rs` 278 行・`results.rs` 502 行・`metadata.rs` 496 行ほか）が HTTP 越しに担保しており、`operation` の内部配置に依存しない。
- したがってフェーズ1 の red に相当するのは「移動の途中でコンパイルが通らない状態」で、green は `cargo test --locked` の全件通過。

**ただし `cargo test --locked` の green だけでは足りない**（計画レビューで採用した指摘 R2・R3）。3 コマンドをすり抜ける失敗が 2 種類ある:

1. **doc コメント・`//!` の消失** — 検出する lint が無い
2. **テストが移動先で実行されなくなる**（`mod tests` の宣言漏れ）— `cargo test` はテスト件数が減っても exit code 0 で終わる

どちらも移動前後の**計数の突き合わせ**で検出する。新しいコマンドは足さず、`grep -c` と `cargo test` の出力の読み方を決めるだけ。移動前の基準値（2026-09-18 に `e4c1826` で実測）:

| 計数 | 基準値 | 移動後の期待 |
|---|---|---|
