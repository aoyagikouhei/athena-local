### 決め手: 検証の順序（GetQueryResults）

**枠組みの検証 → ID の存在 → MaxResults の上限 → クエリの状態 → NextToken の形**

| 順 | 条件 | AthenaErrorCode | Message | 根拠のケース |
| --- | --- | --- | --- | --- |
| 1 | `NextToken` 空文字、`MaxResults` < 1（両方なら nextToken → maxResults の順で 1 文） | `INVALID_INPUT` | `N validation error(s) detected: <制約>; <制約>` | 5, 6, 7, 12, 13, 14, 16, 18, 20, 27 |
| 2 | ID が実在しない | `QUERY_EXECUTION_NOT_FOUND` | `QueryExecution <id> was not found` | 17, 19, **23**（1001 と同時でも NOT_FOUND） |
| 3 | `MaxResults` > 1000 | `INVALID_INPUT` | `MaxResults is more than maximum allowed length 1000` | 4, 15, **26**（FAILED のクエリでも上限のエラー） |
| 4 | 結果が無い（FAILED 等） | `INVALID_QUERY_EXECUTION_STATE` | `Query did not finish successfully. Final query state: FAILED` | 24, **25**（不正なトークンと同時でも状態のエラー） |
| 5 | `NextToken` が不正 | `INVALID_INPUT` | `Malformed nextPageToken <受け取った値>` | 8, 9 |

制約の文言（枠組みの検証。ListWorkGroups の #9 実測と同文）:
- `Value at 'maxResults' failed to satisfy constraint: Member must have value greater than or equal to 1`
- `Value at 'nextToken' failed to satisfy constraint: Member must have length greater than or equal to 1`
- 2 件同時: `2 validation errors detected: <nextToken の制約>; <maxResults の制約>`（ケース 12、**31: ListWorkGroups でも同じ形**）
- `MaxResults` 1001 と `NextToken` 空文字の同時は空文字のエラーだけ（13）。上限超過は枠組みの検証ではない

### 正常系

- `MaxResults` 1000 は通る（3）。`MaxResults` 無しの既定は **列名行込みで 1000 行**（28: 1500 行のクエリで 1000 行 + NextToken、29 も同じ、30: 2 ページ目は 501 行で NextToken 無し）。athena-local の現行の既定 1000 と数え方（列名行込み）は一致
- `NextToken` は長さ 100 の base64 らしい不透明な文字列。正しいトークンで 2 ページ目が取れ、`MaxResults` 1 なら 2 ページ目にも付く（10, 11）
- `UpdateCount` は SELECT でも `0`（1〜3）。ワイヤ上の `ResultSet` には SDK のモデルに無い `ColumnInfos`・`ResultRows` も入っている（範囲外の発見）

## 設計判断

1. **共有する文言と枠組みの検証を新モジュール `src/operation/validation.rs` に置く**（quick では `work_group.rs` に `pub(super)` で置いた）。先行例は `classification.rs`（1 つの判定を複数のオペレーションから呼ぶための共有モジュール。`mod.rs:3-9`、CLAUDE.md:29）。`query_execution.rs` が `work_group.rs` に依存する形は避ける。工学判断で、ユーザーには聞かない
2. **ListWorkGroups も同じ枠組みの検証を通す**（issue 本文の対象は GetQueryResults だが、3 ラウンド目のケース 31 で ListWorkGroups の 2 件同時の形が GetQueryResults と同じと分かった）。現行は `MaxResults` の下限を先に見て 1 件だけ返す。`MaxResults` 51 と空文字の同時は未実測で、上限 50 の文言が枠組みの形（`Member must have value less than or equal to 50`）なので同じ 1 文にまとめる（README の Caveats に未実測と書く）
3. **GetQueryResults の検証の順序は実測の表のとおり**（枠組み → 存在 → 上限 → 状態 → トークンの形）。上限の検査は `store.get` の後、`execution.result` の前に置く
4. **`NextToken` の形の検査は ListWorkGroups と同じ式**（`parse::<usize>().ok().filter(|o| *o < rows.len())`）。文言だけオペレーションごとに違う（`Malformed nextPageToken {token}` と `The nextPageToken is malformed: {token}`。どちらも実測）。`rows` は列名行を外した後の行列で、発行するトークンの基準と同じ
5. **既定ページサイズは 1000 のまま**（実測で列名行込み 1000 行と確認。上限の定数と同じ値なので 1 つの定数にする）
6. **`parse` 失敗時の形（`SerializationException`・必須項目欠落）は変えない**（#84 と TODO.md の別項目。実測値だけ TODO.md に添える）

### `validation.rs` の形（擬似コード）

```rust
//! ページング引数（MaxResults / NextToken）の枠組みの検証。本物は API 定義の制約違反を
//! `N validation error(s) detected: ...` の 1 文にまとめて返す（2026-09-18・09-23 実測）。
pub(super) const MAX_RESULTS_TOO_SMALL: &str = "Value at 'maxResults' failed to satisfy constraint: Member must have value greater than or equal to 1";
pub(super) const NEXT_TOKEN_EMPTY: &str = "Value at 'nextToken' failed to satisfy constraint: Member must have length greater than or equal to 1";
/// 違反があれば INVALID_INPUT の応答。順序は nextToken → maxResults（2 件同時で実測）。
/// `upper` は API 定義に上限があるオペレーション（ListWorkGroups の 50）だけ渡す。GetQueryResults の 1000 は枠組みの検証ではない（別の文言）ので渡さない。
pub(super) fn paging_violation(next_token: Option<&str>, max_results: i32, upper: Option<i32>) -> Option<Response>
fn validation_errors(constraints: &[String]) -> String  // "{n} validation error(s) detected: {a}; {b}"
```
