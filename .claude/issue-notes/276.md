## 実測の手順
- スクリプトのパス: `tools/measure/block-comment-parse-error.sh`（issue #244 で作成。
  #257 で ROUND=3、今回 #276 で ROUND=4 を追加）。
- 実行例（`tools/dev.sh` 経由。DB を省略するか実在しなければ SHOW DATABASES の候補の
  1 件目を自動で使う）:
  ```
  tools/dev.sh OUTPUT=s3://your-bucket/prefix/ DB=your_db ROUND=4 bash tools/measure/block-comment-parse-error.sh
  ```
  S3 Tables・連携カタログの項目（群 F）まで測るなら:
  ```
  tools/dev.sh OUTPUT=s3://your-bucket/prefix/ DB=your_db ROUND=4 \
    S3TABLES_CATALOG=s3tablescatalog/your-bucket S3TABLES_NS=your_ns S3TABLES_TABLE=your_table \
    FEDERATED_CATALOG=your_catalog FEDERATED_DB=your_db FEDERATED_TABLE=your_table \
    bash tools/measure/block-comment-parse-error.sh
  ```
  資格情報はホストのシェルで `AWS_ACCESS_KEY_ID` などを export してから（または
  `~/.aws/credentials`）。
- 必須の環境変数: `OUTPUT`（`s3://bucket/prefix/` の形、末尾に `/`）。
- 任意の環境変数: `DB`・`CATALOG`（既定 AwsDataCatalog）・`REGION`（既定 ap-northeast-1）・
  `OUT_DIR`・`POLL_TIMEOUT`・`RETRY_MAX`・`RETRY_DELAY`（スクリプト先頭のコメントに詳細）。
  加えて群 F 専用: `S3TABLES_CATALOG`・`S3TABLES_NS`・`S3TABLES_TABLE`（3 つとも揃って
  いなければ s3t_ctx_desc・s3t_ctx_msck は未測定）、`FEDERATED_CATALOG`・`FEDERATED_DB`・
  `FEDERATED_TABLE`（3 つとも揃っていなければ fed_ctx_desc・fed_ctx_msck は未測定。
  #257 の時点でこのアカウントに連携カタログは登録されていない）。
- 出力先: `${DEV_HOST_HOME:-$HOME}/athena-block-comment-parse-error-measurements/run-<日時>/`
  （リポジトリの外）。`summary.txt` が実名をマスクした、そのまま貼れる一覧。
- 呼び出し回数: フィクスチャ（H・I・V の作成 3 回・SHOW CREATE TABLE での形式裏取り 2 回）
  + preflight の SHOW TABLES 1 回（DB が実在しなければ SHOW DATABASES も +1）+ 項目
  65 個ぶん（S3TABLES_*・FEDERATED_* が揃っていれば全 65 回、揃っていなければ群 F の
  4 項目が未測定になり 61 回。ただし RENAME TO が決め手の位置にある項目
  （pn5・ar_h0・ar_h2 は H、ar_v0・ar_v2 は V）はどれか 1 つが成功すると後続が
  「改名済みのため未測定」で skip になり、その分だけ呼び出しが減る）+ 後始末
  （元の名前の DROP 3 回 + RENAME 先候補 5 回（`_pn5ren`・`_ar0ren`・`_ar2ren` を H に、
  `_ar0ren`・`_ar2ren` を V に。IF EXISTS なので無害）= 8 回）。
  実測に近い上限は、環境変数ありで 5+1+65+8=79、環境変数なしで 5+1+61+8=75。ドライラン
  （偽 `aws`。すべて SUCCEEDED を返す最悪ケース）で確認した実測値は 76（環境変数あり。
  RENAME TO 系がカスケードで 3 件 skip になった分だけ理論上限の 79 から減った）。
- 課金と DDL: あり。フィクスチャは #244・#257 と同じ 3 つ（`athena_local_probe_244_h`・
  `_i`・`_v`）を作り、最後に DROP する。群 A の r1i（Iceberg の REPLACE COLUMNS で列を
  n・s に作り直す）→ r3i（列 s を s2 に改名）→ 群 B の pn4i（DROP COLUMN n）の順を
  固定し、列名をずらして競合を避ける。群 D の RENAME TO 系（pn5・ar_h0・ar_h2 は H、
  ar_v0・ar_v2 は V）は先着 1 回だけ成功させる設計で、後始末は元の名前と全部の行き先
  候補（`_pn5ren`・`_ar0ren`・`_ar2ren`）に DROP TABLE/VIEW IF EXISTS を投げる。それ
  以外の列を取り合う項目（主に H の pn4・pn6〜pn10・r1h・r3h）は指示どおりの並びで
  投げ、結果は reason.txt の全文で見分ける（ROUND=2 の n5〜n7 と同じ方針）。スキャン
  する SELECT は投げない。群 F は既存の S3 Tables・連携カタログの表を読むだけで、
  新しく作らない。

## 実測の経緯
- 2026-09-27: request-measurement で `tools/measure/block-comment-parse-error.sh` に
  ROUND=4 を追加。issue #276 本文の表の行ごとに群 A〜F に分けて設計した（詳細は
  スクリプト先頭のコメントと項目 ID の表）。
  - 実装側の分岐点（`src/operation/comment_parse_error.rs`・`comment_parse_error/position.rs`・
    `comment_parse_check.rs`）を読み、`detect` が扱う `Target`（ShowCreateTable・Describe・
    MsckRepair・AlterAddColumns・AlterDropColumn・AlterRename）と `scan` が見る 3 位置
    （先頭・キーワードの間・名前の直前）、`valid_name`（4 部未満・引用符無し）、
    `comment_parse_check.rs` の `Probe`（Missing・View・Table{iceberg:false} は同じ扱い、
    Iceberg・NoCatalog・Unknown は forward）を確認した。この時点の main には #257 の
    実装はまだ入っておらず（`git log main --oneline` に #257 のマージが無い、
    `main-257` ブランチも計画のみで `src/` の差分は無い）、`comment_parse_error.rs` は
    まだ「名前の中」「名前の後ろ」「句の中」の位置や REPLACE COLUMNS・CHANGE COLUMN を
    扱っていない（`tests.rs` に「名前の中（未実測。D1）」とある）。ROUND=4 はこれらの
    形を実際の Athena に対して測るだけで、athena-local の実装は変えない。
  - Iceberg 表の ALTER TABLE がコメント入りでも成功する既知の実績（ROUND=3 の g4・
    ri1・ri2・ri3）を踏まえ、群 A の Iceberg 系（r1i・r3i）と群 B の pn4i が同じ列を
    取り合わないよう、r1i で列を n・s に作り直し、r3i は列 s だけを改名し、pn4i は
    その後に列 n を DROP する順に固定した。H・V・M は #244・#257 の実績（ALTER TABLE
    にコメントが決め手の位置にあるとほぼ確実に ParseException になる）から、意図せず
    成功して後続が壊れる見込みは低いとみて、ROUND=2 の n5〜n7 と同じ「指示どおりの
    並びで投げ、結果は reason.txt の全文で見分ける」方針を採った。
  - RENAME TO が決め手の位置にある項目（pn5・ar_h0・ar_h2 は H、ar_v0・ar_v2 は V）は、
    複数本が同じ対象を取り合うため、`H_RENAMED4`／`V_RENAMED4` フラグで先着 1 回だけ
    成功させ、後続は「改名済みのため未測定」で skip する仕組みを足した。
  - ドライラン: `bash -n` に加え、PATH に置いた偽 `aws`（AWS には一切繋がず、すべての
    呼び出しを SUCCEEDED として扱う。python3 で AWS CLI の応答 JSON の形だけ模した）で
    `tools/dev.sh` 経由（toolbox の中）で確認した。
    - ROUND=1・2・3 は、変更前のスクリプト（`git show HEAD:...`）と変更後（このラウンドを
      足した版）で summary.tsv／summary.txt が実行日時の行を除きバイト単位で一致した。
    - ROUND=4 は 65 項目すべてが走り、環境変数（`S3TABLES_*`・`FEDERATED_*`）を渡すと
      群 F の 4 項目も実行された。すべて SUCCEEDED を返す偽 `aws`（最悪ケース）では、
      RENAME TO 連鎖のうち先着 1 回が成功し、残り 3 件（`ar_h0`・`ar_h2`・`ar_v2`）が
      「直前の RENAME TO が成功し H/V が改名済みのため未測定」で正しく skip され、
      summary.txt 冒頭に書く呼び出し回数（76）と `.start-calls` の実際の行数（76）が
      一致した。後始末（`drop-h-pn5ren`・`drop-h-ar0ren`・`drop-h-ar2ren`・
      `drop-v-ar0ren`・`drop-v-ar2ren` を含む）もすべて走った。
    - フィクスチャ作成失敗時の skip 伝播: `CREATE EXTERNAL TABLE` を含む問い合わせだけ
      失敗させる偽 `aws` で H の作成を失敗させたところ、H に依存する全項目
      （g1h・g2h・de1h・g3h・r1h・r3h・pn1〜pn10・de2・pn5・aa_h0・aa_h2・ar_h0・ar_h2・
      nc_drop_awsdc・群 C の全項目）が「H（Hive の EXTERNAL TABLE）を作れなかったため
      未測定」で skip され、`drop-h`・`drop-h-pn5ren`・`drop-h-ar0ren`・`drop-h-ar2ren`
      も（H_OK=0 のため）呼ばれず、I・V に依存する項目と後始末は影響を受けなかった。
    - shellcheck はこの環境・toolbox のどちらにも入っておらず未実行（`bash -n` と
      ドライランで代替。#257 と同じ）。
  - 確かめられなかったこと: 実際の Athena に対する実行（本物の呼び出しはユーザーが
    後で流す）。そのため、群 A の H・V・M で ALTER 系が本当に指示どおりの並びで
    安全か（意図せず成功しないか）は、reason.txt の全文を見るまで確定しない。
- 2026-09-27: 統括役の受け入れ判定で 2 点を直した。(1) 群 E の nc_drop_awsdc を ROUND=4 の最初に移した（RENAME TO の連鎖の後ろにあり、連鎖のどれかが成功すると H が元の名前で無くなって、#256 の位置が測れなかった。CHANGE COLUMN で列 n が消える前でもある）。(2) r3i を `CHANGE COLUMN s s2 string` にした（構文が通ったときに型の変更のエラーと混ざらないように）。本物への呼び出し回数・DDL・秘密の扱いは確認済み。
