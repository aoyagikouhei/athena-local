# 設計チェックリスト

計画（Step 3・Step 6）で読む。1 行 1 項目、出典 issue 番号付き。

- 早期 return の下流に新しい出力（付随ファイルなど）を足すとき、return する経路（本体を書かない文・失敗を握りつぶす腕）のそれぞれでその出力が要るかを、擬似コードで全経路を通して確かめたか（#5 の計画レビューより。「成功の腕から呼ぶ」計画では DML の `.metadata` が一切書けなかった）
- 前処理（正規化・読み飛ばし・整形）を共有関数に切り出して既存の判定に差し込むとき、その判定が使う値を**すべて**列挙し、どれを前処理後・どれを前処理前で渡すかを 1 つずつ決めたか（#17 の計画レビューより。`ResultFile::of` で単語列だけ前処理前のまま残す計画になっており、コメント付き CTAS が別のファイル名に落ちるところだった）
- 差し込む前処理の影響を受ける既存の判定に、先頭の 1 語だけでなく 2 語目以降を見る分岐が無いか grep したか。あるならその分岐も実測とテストの対象に入れたか（#17 の計画レビューより。`.metadata` のクエリ ID を決める分岐だけが 2 語目を見ており、実測項目から漏れていた）
- ファイルを分割・移動する計画で、移す単位を行番号の範囲で指定していないか。関数・定数の直前の `///` ブロックと属性を 1 単位として運ぶ計画になっているか（#19 の計画レビューより。`fn` の行から数えた行番号表が doc コメント 14 行を取りこぼし、「2026-09-17 実測」を含む記録が静かに消えるところだった。`missing_docs` lint が無いので `fmt` / `clippy` / `test` は沈黙する）
- テストを別ファイルへ移す計画に、移動前後のテスト件数を突き合わせる手順があるか（#19 の計画レビューより。`mod tests` の宣言漏れはテスト件数が減るだけで、`cargo test` は exit code 0 の green のまま通る）
