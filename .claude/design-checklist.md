## 設計・実装

- 早期 return の下流に新しい出力（付随ファイルなど）を足すとき、return する経路（本体を書かない文・失敗を握りつぶす腕）のそれぞれでその出力が要るかを、擬似コードで全経路を通して確かめたか（#5 の計画レビューより。「成功の腕から呼ぶ」計画では DML の `.metadata` が一切書けなかった。#70 の計画レビューでも同じ形: 本体を書かない INSERT／CTAS の `.metadata` が、本体用の「到達しない」値を引き継ぐところだった）
- 前処理（正規化・読み飛ばし・整形）を共有関数に切り出して既存の判定に差し込むとき、その判定が使う値を**すべて**列挙し、どれを前処理後・どれを前処理前で渡すかを 1 つずつ決めたか（#17 の計画レビューより。`ResultFile::of` で単語列だけ前処理前のまま残す計画になっており、コメント付き CTAS が別のファイル名に落ちるところだった）
- 差し込む前処理の影響を受ける既存の判定に、先頭の 1 語だけでなく 2 語目以降を見る分岐が無いか grep したか。あるならその分岐も実測とテストの対象に入れたか（#17 の計画レビューより。`.metadata` のクエリ ID を決める分岐だけが 2 語目を見ており、実測項目から漏れていた）
- ファイルを分割・移動する計画で、移す単位を行番号の範囲で指定していないか。関数・定数の直前の `///` ブロックと属性を 1 単位として運ぶ計画になっているか（#19 の計画レビューより。`fn` の行から数えた行番号表が doc コメント 14 行を取りこぼし、「2026-09-17 実測」を含む記録が静かに消えるところだった。`missing_docs` lint が無いので `fmt` / `clippy` / `test` は沈黙する）
- テストを別ファイルへ移す計画に、移動前後のテスト件数を突き合わせる手順があるか（#19 の計画レビューより。`mod tests` の宣言漏れはテスト件数が減るだけで、`cargo test` は exit code 0 の green のまま通る）
- その突き合わせの期待値（ファイルごとの内訳と合計）を、内訳の列挙から数え直して総数と一致させたか（#30 の計画レビューより。列挙は 22 件なのにラベルが「21 件」で、期待値の合計 2+21+3=26 が総数 27 と合わなかった。機械的な突き合わせを用意しても、期待値が誤っていれば正しい結果を誤りと判定して実装者がテストを削る方向に動く）
- ファイルを分割・移動する計画で `use` を配るとき、移した先で実際にその型を使うかを本文の grep で確かめたか（#30 の計画レビューより。使わないファイルに `use serde_json::Value;` を配る計画になっていた。`cargo build` は `unused_imports` を警告としてしか出さずビルドが通るので、抽出ごとの build では気づけず最後の `clippy -D warnings` まで通ってしまう）
- 無害だった近似判定（表示専用のラベル・ログの分類など）を、出力の中身やファイルの有無を左右する分岐に転用していないか。転用するなら、その判定の精度を実測済みの形に絞ったか（#39 の計画レビューより。`SubstatementType` を返すだけだった粗い ALTER 判定を `.metadata` を書くゲートに使う計画になっており、`SET TBLPROPERTIES ('comment' = '...add column...')` の 1 文で実在しない付随ファイルを書くところだった。#70 でも「網羅のためだけ」の placeholder 値が `.metadata` の実値になった）
- 同じ関数の中で、他の腕が位置固定（`word(1)` など）で判定しているのに 1 つの腕だけ全文を走査していないか。揃えれば誤検出が消えないか（#39 の計画レビューより。`CREATE`/`DROP` の腕は位置固定なのに `ALTER` の腕だけ `words.iter().any(...)` で全文を舐めていた）
- 全文走査の判定を位置固定に変えるとき、判定する位置の手前にトリビア（空白・コメント・引用符付き識別子）が挟まる入力を列挙して確かめたか。同じリポジトリの別の場所が同じ書き方に耐性を持たせているなら、新しい判定もそれに合わせたか（#39 の最終パス 2 本と独立レビューが独立に指摘。`ALTER TABLE "my table" ADD COLUMNS` / `cat . ns . t` / `-- comment` / `/* c */` のどれでも、全文走査だった旧実装は通っていたのに位置固定で `None` に落ちた。同じファイル群の `catalog.rs` と `table_format.rs` はこれらの書き方を明示的にサポートしテストしていたので、片方で作った耐性をもう片方が無効化していた）
- 新しい外部への問い合わせを足すとき、その結果を使わない設定・経路でも走ってしまわないか確かめたか（#39 の最終パスより。結果ファイルの書き込みが無効な構成でも形式の問い合わせが毎回走り、`write_result` の入口で結果ごと捨てられていた。往復のぶんだけ遅くなる）
- 既存の問い合わせと同じものを別の段階でもう一度投げるとき、送信の本数・順序を固定した既存テスト（`trino_sqls()` の完全一致など）を grep で全件列挙し、期待値の書き換えを計画の作業に入れたか（#207 の計画レビューより。開始時の存在の確認が実行時と同じ `probe_sql` を投げ、要素数 2 で固定した DESCRIBE のテスト 4 本以上が落ちるところだった）
- 移動・分割を機械的に検証するスクリプトで、値を表示するだけで合否を判定していない項目が無いか。全項目が失敗フラグを立てるかを、わざと壊して確かめたか（#44 の計画レビューより。テスト内訳のチェックが印字だけで、移動境界を 1 つ間違えても総数・doc 行数・実測記録・正規化 diff の 4 項目すべてが ok を返し「すべて ok」で通るところだった）
- 移動元と移動先の**和集合**を突き合わせる検証は、要素がどちらのファイルに属するかを検出しない。属する側を固定する検証を別に持ったか（#44 の計画レビューより。正規化 diff は和集合しか見ないので、残留すべきテストが移動先に入っていても、その逆でも素通りする）
- 挙動を変えない移動の検証に、計画が要求する非純粋変更（可視性の付与・呼び出しパスの修飾）の許容リストを入れたか。入れないと、計画どおり正しく実装するほど確実に NG が出る（#44 の計画レビューより。`pub(super)` の付与 2 件で正規化 diff が必ず落ちる状態だった。#195 の計画レビューでも同じ形: 消す関数の doc にある記録の行 2 つと、テストを別モジュールへ移すことで変わるテスト名 15 本に許容が無く、計画どおり実装すると足場の 2 項目が必ず NG になるところだった）
- 移動・抽出の検証スクリプトの許容リストや折り返しの復元を、仮定の形で書いていないか。cargo fmt に実際に通した出力で「正しい実装が ok になる」側も確かめたか（#175 の計画レビューより。戻り値のタプル型の折り返しを仮定で書き、実測したら復元の perl 自体が区切りの崩れで構文エラーになっていた。わざと壊す確認は NG 側しか見ないので、この欠陥は正しく実装するまで表に出ない。#162 の計画レビューでも同じ形: 改名で消す doc 1 行の許容を計画に書きながら、検証コマンドにその値を渡していなかった。#193 の計画レビューでも同じ形: cargo が `Running unittests` のパスを package 相対で出すのに、workspace の crate のパス `crates/athena-sql/src/lib.rs` を期待した項目が、正しい実装で必ず NG になるところだった。#194 の計画レビューでも同じ形: 呼び出し元の差分を `git diff BASE HEAD` のコミット同士で取る項目が、コミット前の verify では差分 0 で必ず NG になるところだった）
- 「無いことの証拠」（GET が 0 件、STS の呼び出しが 0 件、例外が出ない）で合否を決める判定は、数える範囲を対照と同じ区間（ログの開始行）・接頭辞・パスの前方一致（`.txt` なら `.txt.metadata` も）で閉じたか。足場全体のログを数えると、他のケースが正当に出した行で FAIL になり、先行ケースの行で PASS になる（#111 の計画レビューより。中継ログを全体で数える計画と、`.txt` の直後の文字で `.metadata` を除外する計画が、それぞれ誤った FAIL と誤った PASS を出すところだった）
- 旧版のクライアントや他の版を相手に測るとき、文書に載っている既知の不具合（例: 3.5.1 未満の DDL の NoSuchKey）が、測りたい項目の判定に混ざらないよう、合否の材料をその項目の出力行だけに絞ったか。総括の `failures` や終了コードで判定すると、無関係な既知の失敗で「読めない」と記録される（#111 の計画レビューより）

- ミューテーション（壊す候補）を検出する検証が、壊した機構を実際に通る足場・入力で行われているか。通らない足場だと、壊しても両方 PASS のまま「検出できた」ことになる（#128 の計画レビューより。compose を一度も呼ばない request-errors で、プロジェクト名の引き継ぎの欠落を検証する計画になっていた。#147 の計画レビューでも同じ形: 別プロセスの空のストアに投げる 2 本目は、保持期限の処理が壊れていても期待どおりになる）
- 残骸を数える grep のパターンを、実装前に今のツリーへ当てて「残骸だけに当たる件数」になることを確かめたか。正しく実装しても落ちるパターン（`_default\b` が Rust の `unwrap_or_default` に当たる、`down -v "` が正しい呼び方に当たる）は、実装者が検証を緩める方向に動く（#128 の計画レビューより。5 パターンのうち 4 つが正しい実装で exit 1 になる形だった）

- compose.yml の補間に新しい変数を足すとき、dev（足場を動かすコンテナ）の environment にも同じ名前で引き継いだか。足場は dev の中からも compose を呼び、スクリプトもその変数を読むので、外側の `tools/dev.sh` が export するだけでは dev の中で空になる（#129 の計画レビューより。#128 で DEV_* を引き継いだのと同じ形を、新設の `DEV_HOST_HOME` で落としていた）
- 外部に投げる実行（本物の AWS など）を手元の代役に向けるモードを足すとき、送り先に既定値を持たせず、代役のモードでは資格情報もダミーに差し替えたか。受け入れ判定は送り先を表示するだけでなく期待値と突き合わせて落ちるか（#113 の計画レビューより。生 HTTP の 4 項目のどれか 1 つで上書きが漏れると、ドライランのつもりで署名付きのリクエストが本物に飛ぶ形だった）
- 1 時間を超える一発勝負の実行で、後始末を最後にまとめていないか。一時的な資格情報（既定 1 時間）が切れると、最後の後始末ごと失敗して本番に残る。後始末は作った項目の直後に行い、trap は保険にしたか（#113 の計画レビューより）
- ユーザーが事前に用意する設定（出力先を設定したワークグループなど）を、実行の前に機械で確かめて止まるか。過去の実測で「用意したつもり」の skip を繰り返していないか（#113 の計画レビューより。WORKGROUP2 の出力先が 2 回とも未設定で、3 回目も同じ形だった）
- 手元の代役で決まる答え（代役の実装から決めた期待値）を、本物に向けた実行でも照合していないか。本物の答えを測る項目で照合すると、測りたい新事実が「期待と違う」に見える。照合は代役のときだけにし、本物では事実だけを記録したか（#113 の最終パス 2 本が独立に指摘。トークンの 4 項目だけガードが抜けていた）
- 実測の対照（コントロール）の文は、過去に本物で成功した形をそのまま使ったか。対照に新しい要素（未測の型の綴りなど）を混ぜると、対照が落ちたときに本題の失敗と切り分けられず、1 ラウンド無駄になる（#146 の計画レビューより。`REPLACE COLUMNS` の対照だけ #43 の成功形と違う `varchar` を使っていた）
- 手元の代役が既定で補う値（出力先など）を、本物に投げる経路のすべての呼び出しで明示しているか。代役に向けたドライランはその値が無くても通るので、本物で初めて全滅する（#146 の 1 回目の実測より。`run_stmt` の既定が「付けない」で、19 項目と後始末の DROP が `No output location provided` になるところだった。過去の実測スクリプトはすべて明示していた）
- 「既定を当てる前の生の値で比べる」型の判定を固定するテストに、「省略」と「既定と同じ値の明示」の対を入れたか。明示→明示の対だけだと、既定を当てた後の値で比べる実装に書き換えても通る（#150 の計画レビューより。Catalog を足すテストが明示の 2 本だけで、Database の既存ケースも既定と違う値を明示していた）
- 「確認できなければ安全側に倒す」関数の戻り値の向きを、呼び出し側の `if` と突き合わせたか。コメントとログが安全側と書いていても、戻り値が逆だと失敗時に危険側へ進む（#113 の独立レビューと最終パスが独立に指摘。SHOW TABLES の失敗が「同名は無い → 作る」に倒れていた）

## 文書（README・CHANGELOG）

- 既存の「対象の文 × 条件」で分岐する機構（テーブルの形式で結果ファイルを書き分ける等）に新しい文を足すとき、docs の対象の表だけでなく「判定できないときにどう倒れるか」の節も対象に入れたか。倒れ先の記述（空ファイル・`.metadata` なし）は元の文の前提で書かれていて、新しい文では嘘になる（#151 の計画レビューで 2 本が独立に指摘。`docs/ddl.md` の表だけを直す計画になっていた）
- 表や一覧に載せた書き方が、そのプロジェクトで実際に通るか確かめたか。通らないなら、注意を離れた節に書かずにその表の直下へ置いたか（#39 の README レビューより。`ALTER TABLE ... ADD COLUMNS` を表の見出しに載せながら、その綴りが Trino で構文エラーになることを 100 行以上離れた Caveats にしか書いておらず、表を見て試した読者が理由にたどり着けなかった）
- 同じ事実を複数の節に書くとき、正を 1 か所に決めて、ほかは「例外がある」とだけ述べてリンクに任せたか（#39 の README レビューより。同じ事実が 7 か所に、同じ節への参照が 5 回出ていた。中身を全部言い直したあとで「詳細は下記」と書くと、参照する意味が無くなる）
- README に `now` / `old` のような時間軸の言葉を入れていないか。変更の記録は CHANGELOG の語彙で、README だけを読む人には何を指すのか分からない（#39 の README レビューより。同じ issue で両方を書いたため混ざった）
- 同じものを指す呼び名が揺れていないか。1 つ決めて使い回したか（#39 の README レビューより。同じ振る舞いに 3 通り、同じ仕組みに 4 通りの呼び名が付いていた）

- 字句処理の境界（語・トークンの切れ目）の規則を広げるとき、「空白でも識別子でもない」バイト（制御文字 `\x0B`・`\x0C`、非 ASCII の空白 `U+3000`・`U+00A0`）がどちら側に入るかを決め、既存の固定表でそれらの行が動かないかを確かめたか（#200 の計画レビューより。「識別子の文字以外はすべて境界」にする計画で、固定表の 4 行が予測表に無いまま DML／Csv に反転するところだった。Trino はこれらを構文エラーにするので、境界は ASCII の記号に絞った）
- SQL を全文走査する字句処理を新しく書くとき、引用符の中を `skip_quoted` で飛ばしてからコメント（`--`／`/*`）を見ているか。リテラルの中の `--` をコメントと読むと、S3 Express のバケット名（`a--b--x-s3`）を含む 1 行の CTAS で文末までが消えて `AS SELECT` を見失う（#52 の計画攻撃より。`alias_qualified_names` は引用符 → コメントの順で見ていて、新しい `words()` だけがその順序を外していた）

## 出荷（コミットする前）

- `git add -A` の前に、新規ファイル（`git status` の `??`）を 1 つずつ見たか。とくに委譲先が作ったディレクトリには、ビルド成果物・秘密鍵・証明書・ログが混ざりうる（#39 より。JDBC の足場のビルド成果物 32MB と、TLS の秘密鍵を公開リポジトリにコミットした。前者は委譲先が「`.gitignore` の対象かどうかは未確認」と報告に明示していた）
- `.gitignore` のパターンが、リポジトリ直下だけでなくネストしたディレクトリにも効くか確かめたか（#39 より。`/target` は Rust の直下しか無視せず、ネストした `jdbc-client/target/`（今の `tools/e2e/minio/jdbc-client/target/`）に効いていなかった）
- 出荷時点で未実施の人間検証リストを、PR 本文に書くだけでなく**起票**したか（#39 より。PR とコメントには書いたが起票を忘れ、マージ後に指摘された）
- 実測の項目を依頼する前に、項目ごとに既存の生データを SQL の先頭語（`DESC`・`SHOW SCHEMAS` など）で grep したか。ラベル名だけで探すと、別 issue のラウンドに残っている答え（#70 の `f1-desc`）を見落として本物に 1 本余分に投げる（#173 の計画レビューより）
- 値を差し替えて既存の関数に渡すとき、その値が「利用者側の名前（Athena のカタログ名・別名のキー）」か「実行先の名前（Trino のカタログ名）」かを、受け取る関数の前提（別名のキーなら問い合わせない等）と突き合わせたか（#214 の計画レビューより。別名のキーを返す計画だと存在の確認が飛んだ）
- 「未実測なので弾かない（実行する）」に倒す条件が、実測済みの形まで巻き込んでいないか。条件を実測した表と 1 行ずつ突き合わせ、未実測の部分（名前の部品数・後ろの句）だけを外したか（#208 の計画レビューより。`(LIKE <1 部>)` だけが未実測なのに `LIKE` 全体を外し、実測済みの `(LIKE <db>.<t>)` を取りこぼす計画だった）
